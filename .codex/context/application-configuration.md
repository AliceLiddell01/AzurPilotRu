# Пользовательская конфигурация приложения

Владелец: этот файл. Здесь описаны схема конфигурации, runtime-путь файла, правила загрузки и
валидации, владелец встроенных значений по умолчанию и стабильные отказы конфигурации. Коды отказов,
признак повторяемости и structured details принадлежат [application-failures.md](application-failures.md);
логирование и диагностический snapshot — [runtime-diagnostics.md](runtime-diagnostics.md); содержание
проверок — [verification.md](verification.md); карта проекта — [architecture.md](architecture.md).

## Роль конфигурации

Конфигурация приложения — одна реальная capability текущего этапа: строгий типизированный
пользовательский документ, который application host загружает один раз при запуске. Секции будущих
capability (MuMu, ADB, lifecycle игры, screenshot/vision, input, OCR) в схему не добавляются:
секция появляется вместе с реализацией capability, а не заранее. Product identity игры
(регион/сервер/пакет) также не является настройкой конфигурации: реальный потребитель этого
контракта появится вместе с ADB/game lifecycle.

## Runtime-путь

Владелец пути — `AzurPilotConfigurationPath.GetDefaultRuntimePath()` в
`src/AzurPilot.Core/Configuration/`: это `%LOCALAPPDATA%\AzurPilot\config.json`, вычисленный через
BCL API (`Environment.SpecialFolder.LocalApplicationData`). Абсолютная строка пути конкретной машины
в репозитории запрещена ([architecture.md](architecture.md)), поэтому второй владелец пути — в том
числе в документации — не заводится.

Приложение не создаёт каталог конфигурации и не пишет файл: отсутствие каталога или файла —
валидный сценарий запуска, а не ошибка. Startup сам вычисляет runtime-путь через владельца
`AzurPilotConfigurationPath`: пользовательской опции выбора пути и любого CLI у приложения нет.
Явно переданный путь существует только как код-параметр composition — это seam, которым тесты
указывают временный файл, не подменяя пользовательскую конфигурацию.

## Схема v1

Версия схемы, которую понимает текущая сборка, принадлежит константе
`AzurPilotConfiguration.CurrentSchemaVersion`; загрузчик, встроенные defaults и тесты используют её, а
не собственную копию числа. JSON-документ схемы v1 состоит из двух обязательных свойств:

```json
{
  "schemaVersion": 1,
  "diagnostics": {
    "minimumLevel": "Information"
  }
}
```

Правила схемы:

- `schemaVersion` — обязательное целое число; документ без него невалиден, а значение, отличное от
  поддерживаемой версии, означает неподдерживаемую схему;
- `diagnostics.minimumLevel` — обязательная JSON-строка с точным именем уровня логирования;
  допустимые имена — это имена типа `LogLevel` из logging stack, поэтому Core не хранит вторую копию
  их перечня. Числовая форма, неизвестное имя и произвольный регистр отвергаются как несоответствие
  схеме;
- имена свойств заданы явно в camelCase: строгая десериализация сравнивает имена с учётом регистра,
  поэтому контракт не зависит от политики именования;
- метаданные типов приходят из source-generated контекста — reflection-based десериализация
  конфигурации не используется.

Example-config в репозитории не создаётся: он стал бы вторым владельцем тех же значений, который
пришлось бы синхронизировать с defaults отдельными проверками.

## Владелец значений по умолчанию

Встроенные значения по умолчанию существуют ровно в одном месте — `AzurPilotConfigurationDefaults` в
`src/AzurPilot.Core/Configuration/`. Сценарий «файла нет» и любое будущее использование defaults
обязаны обращаться туда. Встроенная конфигурация описывает ту же схему v1, что и файл, поэтому
проходит те же проверки.

## Строгость JSON

Владелец JSON-контракта — `AzurPilotConfigurationJson` в `src/AzurPilot.Core/Configuration/`: строгие
опции строятся на `JsonSerializerOptions.Strict`, а экземпляр опций дополнительно документирует
camelCase-имена. Из-за этого отказов конфигурации заведомо больше двух, поэтому правило формулируется
как перечень гарантий, а не как перечень кодов:

- неизвестное свойство на любом уровне, включая секции будущих capability, — отказ;
- duplicate property — отказ;
- неверный регистр имени свойства или значения — отказ;
- нарушение required/nullable contract — отказ;
- trailing comma, комментарий, числовая форма значения перечисления, неверный тип `schemaVersion` —
  отказ;
- синтаксически невалидный или пустой документ, документ без JSON-объекта в корне — отказ.

Отклонения в сторону строгости осознанны и зафиксированы в XML-doc типов:

- для `minimumLevel` используется собственный строгий конвертер, а не `JsonStringEnumConverter`,
  который сравнивает имена без учёта регистра и принимает числовую форму, то есть пропускал бы
  документ вне схемы v1;
- `schemaVersion` извлекается до строгой десериализации, поэтому файл более новой схемы получает
  отказ о неподдерживаемой версии, а не сообщение о неизвестном свойстве. Документ более новой схемы
  неизбежно содержит новые секции, и оператор должен видеть причину, которую может исправить;
- существующий, но нечитаемый файл даёт отказ, а не подстановку defaults: иначе сбой чтения выглядел
  бы как отсутствие конфигурации.

## Правила загрузки

Загрузчик — `AzurPilotConfigurationLoader.Load(string path)`: он принимает явный абсолютный путь и
возвращает `ApplicationResult<AzurPilotConfigurationSnapshot>`. Правила:

- отсутствие файла или каталога — успешная загрузка встроенных defaults; файл при этом не создаётся;
- существующий файл читается полностью и валидируется; невалидный файл никогда не подменяется
  defaults, а даёт явный отказ;
- файл читается как UTF-8; ведущий BOM допускается, потому что относится к кодировке файла, а не к
  JSON-документу, и строгость не ослабляет;
- относительный, пустой или состоящий из пробелов путь — ошибка программирования вызывающей стороны
  (исключение), а не ожидаемый отказ загрузки;
- конфигурация читается один раз: автоматического file watcher и reloadOnChange нет.

Snapshot — `AzurPilotConfigurationSnapshot`: immutable конфигурация вместе с источником (встроенные
defaults или файл) и путём файла. Создать snapshot вручную нельзя, поэтому snapshot всегда
провалидирован, а изменение или удаление файла после загрузки на него не влияет: перезагрузка
конфигурации на этом этапе не поддерживается.

## Отказы конфигурации

Стабильные коды отказа, признак повторяемости, состав details и коды выхода процесса принадлежат
[application-failures.md](application-failures.md) — здесь дублируется только соответствие «ситуация →
код», чтобы владелец конфигурации оставался читаемым:

| Ситуация | Код отказа |
| --- | --- |
| Существующий файл не читается или не соответствует схеме v1 | `configuration_invalid` |
| Версия схемы в файле не поддерживается этой сборкой | `configuration_schema_unsupported` |
| Файла или каталога конфигурации нет | отказа нет: загрузка успешна на встроенных defaults |

Отказы конфигурации не помечаются retryable: файл должен исправить оператор, а повтор той же
загрузки без изменения файла ничего не изменит. Оба отказа несут в details путь конфигурации, а отказ
о неподдерживаемой схеме — ещё и версию схемы из файла.

## Границы capability

- Конфигурация не собирается из нескольких источников: `Microsoft.Extensions.Configuration` не
  агрегирует пользовательскую конфигурацию, а строгий JSON snapshot передаётся в DI как готовый
  объект ([runtime-diagnostics.md](runtime-diagnostics.md)).
- Hot reload, `config reload`, продуктовая опция выбора пути к файлу конфигурации и example-config не
  вводятся.
- Диагностика сообщает о конфигурации bounded сведения (источник, версия схемы, статус валидации,
  минимальный уровень логирования) и не печатает полный документ.
