# Пользовательская конфигурация приложения

Владелец: этот файл. Здесь описаны схема конфигурации, runtime-путь файла, правила загрузки и
валидации, нормализация legacy-схемы, владелец встроенных значений по умолчанию и стабильные отказы
конфигурации. Коды отказов, признак повторяемости и structured details принадлежат
[application-failures.md](application-failures.md); логирование и диагностический snapshot —
[runtime-diagnostics.md](runtime-diagnostics.md); содержание проверок — [verification.md](verification.md);
карта проекта — [architecture.md](architecture.md).

## Роль конфигурации

Конфигурация приложения — строгий типизированный пользовательский документ, который application host
загружает один раз при запуске. Секции capability, которых в приложении ещё нет (ADB, lifecycle игры,
screenshot/vision, input, keymap, разрешение экрана, OCR), в схему не добавляются: секция появляется
вместе с реализацией capability, а не заранее. Секция `mumu` появилась вместе с capability MuMu и
содержит ровно одну реальную настройку — выбор Android-экземпляра. Product identity игры
(регион/сервер/пакет) настройкой конфигурации не является: её потребитель появляется вместе с
ADB/game lifecycle.

## Runtime-путь

Владелец пути — `AzurPilotConfigurationPath.GetDefaultRuntimePath()` в
`src/AzurPilot.Core/Configuration/`: это `%LOCALAPPDATA%\AzurPilot\config.json`, вычисленный через
BCL API (`Environment.SpecialFolder.LocalApplicationData`). Абсолютная строка пути конкретной машины
в репозитории запрещена ([architecture.md](architecture.md)), поэтому второй владелец пути — в том
числе в документации — не заводится.

Приложение не создаёт каталог конфигурации и не пишет файл: отсутствие каталога или файла —
валидный сценарий запуска, а не ошибка. Startup сам вычисляет runtime-путь через владельца
`AzurPilotConfigurationPath`: пользовательской опции выбора пути и любого CLI у приложения нет.
Явно переданный путь существует только как код-параметр composition — это seam, которым тесты
указывают временный файл, не подменяя пользовательскую конфигурацию.

## Схема v2

Версия схемы, которую понимает текущая сборка, принадлежит константе
`AzurPilotConfiguration.CurrentSchemaVersion`; загрузчик, встроенные defaults, нормализация
legacy-входа и тесты используют её, а не собственную копию числа. Эффективная схема v2 состоит из трёх
обязательных свойств:

```json
{
  "schemaVersion": 2,
  "diagnostics": {
    "minimumLevel": "Information"
  },
  "mumu": {
    "instance": "auto"
  }
}
```

Правила схемы:

- `schemaVersion` — обязательное целое число; документ без него невалиден. Поддерживаемые версии —
  эффективная v2 и legacy-вход v1 (см. ниже); любой другой номер означает неподдерживаемую схему;
- `diagnostics.minimumLevel` — обязательная JSON-строка с точным именем уровня логирования;
  допустимые имена — это имена типа `LogLevel` из logging stack, поэтому Core не хранит вторую копию
  их перечня. Числовая форма, неизвестное имя и произвольный регистр отвергаются как несоответствие
  схеме;
- `mumu.instance` — обязательная JSON-строка; допустимы ровно две формы: литерал `auto` (экземпляр
  выбирает провайдер) и провайдерская форма `mumu:<digits>`, например `mumu:1`, где `<digits>` —
  неотрицательное целое без ведущих нулей, кроме самого `0`. Всё остальное — пустая строка, display
  name, `1`, `mumu:`, `mumu:01`, `mumu:-1`, нестроковый тип — несоответствие схеме. Синтаксис значения
  принадлежит единственному владельцу `MuMuInstanceValue` в `src/AzurPilot.Core/Configuration/`, а
  строгий JSON-конвертер значения только вызывает его: второй копии грамматики нет. Литерал `auto`
  сравнивается с ordinal-семантикой, поэтому `Auto` и `AUTO` схемой не являются;
- секция `mumu` содержит только `instance`: настройки ADB, lifecycle игры, screenshot/vision, input,
  keymap, разрешения экрана, OCR и override пути установки в неё не добавляются;
- имена свойств заданы явно в camelCase: строгая десериализация сравнивает имена с учётом регистра,
  поэтому контракт не зависит от политики именования;
- метаданные типов приходят из source-generated контекста — reflection-based десериализация
  конфигурации не используется.

Example-config в репозитории не создаётся: он стал бы вторым владельцем тех же значений, который
пришлось бы синхронизировать с defaults отдельными проверками.

## Legacy-вход схемы v1 и нормализация в памяти

Документ с `schemaVersion = 1` и единственной секцией `diagnostics` допускается как legacy-вход: он
читается строго своим контрактом и нормализуется к эффективной схеме v2 **в памяти** — прочитанная
диагностика сохраняется, а значения, которых в схеме v1 не было, в том числе `mumu.instance = "auto"`,
приходят от владельца встроенных defaults. Правила:

- нормализация существует только в памяти: файл v1 не перезаписывается, не создаётся и не
  ремонтируется. Migration/repair/update команды, отдельный CLI и шаг «обновить конфигурацию» не
  вводятся; единственная публичная операция загрузчика остаётся
  `AzurPilotConfigurationLoader.Load(string path)`;
- строгость v1 не ослабляется: секция `mumu` для контракта v1 — неизвестное свойство, поэтому документ
  v1 с ней невалиден, как и любой другой документ, не соответствующий своему контракту;
- нормализация не делает валидным невалидный документ: невалидный v1 отклоняется так же, как раньше;
- snapshot несёт и версию схемы источника, и версию эффективной схемы, поэтому нормализованный
  legacy-вход отличим от документа v2 без дампа конфигурации.

## Владелец значений по умолчанию

Встроенные значения по умолчанию существуют ровно в одном месте — `AzurPilotConfigurationDefaults` в
`src/AzurPilot.Core/Configuration/`. Сценарий «файла нет», нормализация legacy-входа и любое будущее
использование defaults обязаны обращаться туда. Встроенная конфигурация описывает ту же схему v2, что
и файл, поэтому проходит те же проверки, а встроенное `mumu.instance = "auto"` существует ровно один
раз — у этого владельца.

## Строгость JSON

Владелец JSON-контракта — `AzurPilotConfigurationJson` в `src/AzurPilot.Core/Configuration/`: строгие
опции строятся на `JsonSerializerOptions.Strict`, а экземпляр опций дополнительно документирует
camelCase-имена. Строгость применяется к каждой поддерживаемой source schema её собственным контрактом,
поэтому неизвестное свойство для v1 (включая секцию `mumu`) и неизвестное свойство для v2 отвергаются
одинаково. Из-за этого отказов конфигурации заведомо больше двух, поэтому правило формулируется
как перечень гарантий, а не как перечень кодов:

- неизвестное свойство на любом уровне, включая секции будущих capability, — отказ;
- duplicate property — отказ;
- неверный регистр имени свойства или значения — отказ;
- нарушение required/nullable contract — отказ;
- trailing comma, комментарий, числовая форма значения перечисления, неверный тип `schemaVersion` —
  отказ;
- синтаксически невалидный или пустой документ, документ без JSON-объекта в корне — отказ.

Отклонения в сторону строгости осознанны и зафиксированы в XML-doc типов:

- для `minimumLevel` используется собственный строгий конвертер, а не `JsonStringEnumConverter`,
  который сравнивает имена без учёта регистра и принимает числовую форму, то есть пропускал бы
  документ вне схемы; для `mumu.instance` — собственный строгий конвертер, который вызывает владельца
  синтаксиса и не хранит собственную грамматику;
- `schemaVersion` извлекается до строгой десериализации, поэтому файл более новой схемы получает
  отказ о неподдерживаемой версии, а не сообщение о неизвестном свойстве. Документ более новой схемы
  неизбежно содержит новые секции, и оператор должен видеть причину, которую может исправить;
- повторяющееся свойство в корне документа отклоняется уже при определении версии схемы: версия
  выбирает контракт десериализации, поэтому решение принимается по однозначному документу, и документ
  с двумя `schemaVersion` не может получить «неподдерживаемая версия» вместо «несоответствие схеме».
  Повторяющиеся свойства внутри секций по-прежнему проверяет строгая десериализация, поэтому приоритет
  «неподдерживаемая версия важнее строгой проверки секций будущей схемы» сохраняется;
- существующий, но нечитаемый файл даёт отказ, а не подстановку defaults: иначе сбой чтения выглядел
  бы как отсутствие конфигурации.

## Правила загрузки

Загрузчик — `AzurPilotConfigurationLoader.Load(string path)`: он принимает явный абсолютный путь и
возвращает `ApplicationResult<AzurPilotConfigurationSnapshot>`. Правила:

- отсутствие файла или каталога — успешная загрузка встроенных defaults схемы v2; файл при этом не
  создаётся;
- существующий файл читается полностью и валидируется контрактом своей версии; невалидный файл никогда
  не подменяется defaults, а даёт явный отказ;
- версия схемы определяет контракт: v2 читается контрактом эффективной схемы, v1 — legacy-контрактом с
  нормализацией в памяти, неподдерживаемый номер даёт отдельный стабильный отказ;
- файл читается как UTF-8; ведущий BOM допускается, потому что относится к кодировке файла, а не к
  JSON-документу, и строгость не ослабляет;
- относительный, пустой или состоящий из пробелов путь — ошибка программирования вызывающей стороны
  (исключение), а не ожидаемый отказ загрузки;
- конфигурация читается один раз: автоматического file watcher и reloadOnChange нет.

Snapshot — `AzurPilotConfigurationSnapshot`: immutable конфигурация вместе с источником (встроенные
defaults или файл), путём файла и обеими версиями схемы — версией, которую объявил источник, и версией
эффективной схемы (для встроенных defaults они совпадают). Создать snapshot вручную нельзя, поэтому
snapshot всегда провалидирован, а изменение или удаление файла после загрузки на него не влияет:
перезагрузка конфигурации на этом этапе не поддерживается.

## Отказы конфигурации

Стабильные коды отказа, соответствие «ситуация → код», признак повторяемости, состав details и коды
выхода процесса принадлежат [application-failures.md](application-failures.md): второй перечень здесь
не заводится.

Правило этого документа: отсутствие файла или каталога конфигурации отказом не является — загрузка
успешна на встроенных defaults. Существующий файл, который не читается или не соответствует схеме
своей версии, напротив, никогда не подменяется defaults и даёт явный отказ.

Отказы конфигурации не помечаются retryable: файл должен исправить оператор, а повтор той же
загрузки без изменения файла ничего не изменит.

## Границы capability

- Конфигурация не собирается из нескольких источников: `Microsoft.Extensions.Configuration` не
  агрегирует пользовательскую конфигурацию, а строгий JSON snapshot передаётся в DI как готовый
  объект ([runtime-diagnostics.md](runtime-diagnostics.md)).
- Hot reload, `config reload`, продуктовая опция выбора пути к файлу конфигурации, example-config и
  migration/repair/update конфигурации не вводятся.
- Диагностика сообщает о конфигурации bounded сведения (источник, версия схемы, статус валидации,
  минимальный уровень логирования) и не печатает полный документ; состав диагностического snapshot
  принадлежит [runtime-diagnostics.md](runtime-diagnostics.md).
