# AzurPilotRu: управление документацией и agent context

## Назначение

Этот skill владеет процедурой размещения и оформления **постоянного знания** репозитория.
Его цель — сохранить документацию полной, но не платить за неё постоянным контекстом агента.

Главный принцип:

> Сначала выбери владельца знания, затем пиши текст. Не выбирай `.codex/context/` по умолчанию.

Подробная матрица размещения — `references/placement.md`.
Правила краткости, примеров и форматирования — `references/style-and-examples.md`.

## Пять типов владельцев

1. **Machine-readable source** — код, schema, manifest, config, test contract. Используй его для точных
   значений, которые система уже может прочитать сама.
2. **`AGENTS.md`** — только глобальные invariants и routing, реально полезные почти для любой задачи.
3. **`.codex/context/`** — короткие agent-critical ограничения конкретной области: то, нарушение чего
   с высокой вероятностью приведёт к неправильной реализации.
4. **`docs/`** — архитектурное объяснение, rationale, примеры, usage, troubleshooting, verification,
   acceptance evidence и подробные reference-материалы.
5. **`.agents/skills/`** — повторяемая процедура работы агента: последовательность действий, triage,
   шаблон проверки, публикация и подобные workflow.

Одно утверждение имеет одного основного владельца. Остальные места ссылаются на него или дают
короткое task-routing описание без повторения содержания.

## Рабочий процесс

### 1. Установи фактическое состояние

Перед документированием проверь актуальный код, tests, manifests и текущий diff. Не превращай
описание намерения из prompt/PR body в факт, если реализация говорит другое.

### 2. Разложи каждое новое утверждение по владельцам

Для каждого утверждения спроси:

- это точное значение, которое уже выражено кодом/schema/manifest? → не копируй значение в prose;
- это глобальный запрет/инвариант для большинства задач? → кандидат в `AGENTS.md`;
- агенту нужно помнить это именно при изменении данной capability? → кандидат в `.codex/context/`;
- это объясняет «как устроено/почему/как использовать/как диагностировать/что доказано»? → `docs/`;
- это описывает «как агент должен выполнять повторяемую процедуру»? → skill.

Если утверждение попадает сразу в несколько категорий, выбери канонического владельца и оставь ссылки.

### 3. Сначала разгрузи, потом добавляй

Если изменение расширяет существующий context-файл, проверь, можно ли одновременно вынести из него
объяснения, evidence или устаревшие детали в `docs/`.

Рост agent context должен объясняться новым decision-critical invariant, а не размером feature.

### 4. Обнови маршрутизацию

При появлении нового владельца:

- `AGENTS.md` меняй только если нужен глобальный route;
- `.codex/context/INDEX.md` меняй только для agent-context маршрутизации;
- `docs/README.md` меняй для человеческой документации;
- не создавай две параллельные таблицы владельцев с одинаковой детализацией.

### 5. Проверь ссылки и дубли

Перед завершением:

- найди семантически повторённые правила между `AGENTS.md`, context, docs и skills;
- замени повтор ссылкой или коротким route;
- проверь относительные ссылки;
- убедись, что context не содержит machine-specific acceptance history;
- убедись, что docs не выдают устаревший runtime evidence за вечный контракт.

## Что нельзя писать в `AGENTS.md`

Не помещай туда:

- подробный обзор каждой capability;
- build/test tutorial и длинные команды, если они имеют другого владельца;
- списки классов/файлов;
- acceptance results;
- troubleshooting;
- примеры реализации;
- историю решений;
- task-specific HOW.

Если правило относится лишь к небольшой области проекта, route к её context/doc лучше глобального текста.

## Что нельзя писать в `.codex/context/`

По умолчанию запрещены:

- «доказано на моей машине», версии локальной MuMu/ADB/Android и конкретные результаты прогона;
- длинные таблицы evidence;
- полные stdout/stderr и логи;
- tutorial и пошаговая установка;
- troubleshooting для пользователя;
- история PR/roadmap/review;
- список всех тестов и подробный пересказ CI;
- полный каталог кодов/версий/defaults, если они уже принадлежат коду или manifest;
- длинные HOW-примеры и implementation walkthrough;
- объяснение каждой альтернативы, которую когда-то рассматривали;
- будущие capability и placeholder-контракты.

Допустим короткий пример, только если без него invariant остаётся двусмысленным.

## Что обязано оставаться в context

Не сокращай ценой correctness. В context остаются:

- ownership/boundary, который нельзя безопасно вывести локально;
- fail-closed семантика и различия состояний, легко теряемые при «упрощении»;
- запрещённые fallback/recovery, способные затронуть другой target или source of truth;
- concurrency/lifecycle invariants;
- важные negative contracts;
- точка, где agent должен перейти к более подробному doc или machine-readable owner.

## Завершение feature

При завершении substantial feature не выполняй ритуал «создать новый context-файл».
Сначала классифицируй появившееся durable knowledge.

Новая capability может потребовать одновременно:

- несколько строк routing;
- короткий agent contract;
- подробный architecture doc;
- обновление getting-started или troubleshooting;
- новый skill — только если появилась новая повторяемая процедура.

Количество артефактов определяется реальной ответственностью, а не размером diff.

## Финальная проверка

Перед публикацией изменения документации должно быть истинно:

- `AGENTS.md` остаётся коротким глобальным контрактом;
- context читается как набор решений/ограничений, а не учебник;
- подробности доступны в `docs/`, а не потеряны ради сокращения;
- точные значения не имеют второго prose-owner без необходимости;
- skill содержит procedure, а не архитектурную энциклопедию;
- examples короткие и объясняют границу;
- ссылки ведут к актуальным владельцам;
- добавленный текст не содержит воды и повторов.
