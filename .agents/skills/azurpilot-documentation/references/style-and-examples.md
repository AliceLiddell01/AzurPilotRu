# Стиль документации и примеров

## Пиши от решения, а не от истории

Предпочитай:

> Endpoint разрешается только из сведений выбранного экземпляра; fallback и вычисление порта запрещены.

Не пиши:

> Сначала мы попробовали один вариант, потом заметили проблему, после нескольких тестов решили…

История нужна только когда без неё невозможно понять rationale; тогда ей место в `docs/`, а не context.

## Один абзац — одна мысль

Избегай длинных вводных, повторяющих название раздела. Если заголовок уже сообщает предмет, начинай с
контракта или факта.

Плохо:

> В этом разделе мы рассмотрим правила, связанные с тем, как именно выполняется…

Хорошо:

> Все device-команды используют `-s <endpoint>`.

## Примеры

Пример в agent context допустим, если он снимает неоднозначность быстрее, чем дополнительная проза.

Хорошо:

> Разрешено: `connect <endpoint>` и затем `-s <endpoint> ...`.  
> Запрещено: выбрать первый результат `adb devices`.

Плохо: двадцать строк реального stdout ADB и разбор каждого поля. Такой материал перенеси в `docs/`.

## Таблицы

Используй таблицу, когда читателю нужно сравнивать значения по одинаковым измерениям.
Не превращай таблицу в способ спрятать длинный prose-каталог.

Если строки таблицы повторяют machine-readable enum/manifest, таблица должна иметь отдельную ценность
для человека; иначе поставь ссылку на owner.

## Код и команды

- В context показывай только минимальный синтаксис, нужный для ограничения.
- В docs можно давать команды и примеры вывода, но не копируй machine-specific абсолютные пути.
- Большой patch или implementation walkthrough не является документацией контракта.
- Точные идентификаторы, class/function names и config keys сохраняй без перевода.

## Evidence

В durable docs различай:

- **контракт** — что система обязана делать;
- **текущее устройство реализации** — что делает код сейчас;
- **наблюдение** — что было подтверждено конкретным runtime/acceptance прогоном.

Наблюдение не превращай в универсальное правило без основания.

## Контроль воды

Удаляй предложение, если после его удаления:

- не меняется понимание контракта;
- не теряется rationale;
- не теряется способ использования/диагностики;
- не теряется существенное evidence;
- не исчезает важная ссылка на owner.

Повтор той же мысли другими словами — не усиление правила, а расход контекста.
