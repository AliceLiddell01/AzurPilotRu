# Публикация: ветка, staging, commit, push и remote postcondition

Этот файл владеет порядком действий обычной публикуемой задачи до подтверждённого
удалённого состояния. Контракт и границы задаёт `SKILL.md`.

Команды ниже предназначены для PowerShell в текущем Windows checkout.
`$remote` и `$branch` устанавливай только после проверки фактических remote,
upstream и рабочей ветки; `$taskPaths` — массив только принадлежащих задаче
путей. Не запускай команды с неинициализированными переменными и не
переноси их в Bash/WSL2 ради примеров.

## 1. Установить фактическое состояние checkout

Перед первой операцией записи установи идентичность репозитория и текущее
состояние:

```powershell
git rev-parse --show-toplevel
git remote -v
git rev-parse --abbrev-ref HEAD
git status --porcelain
git rev-parse HEAD
```

Перед публикацией обнови remote refs:

```powershell
git fetch $remote --prune
```

Если checkout относится не к ожидаемому репозиторию либо нельзя однозначно
установить текущую ветку/upstream, не угадывай и не переключай ветки молча.

## 2. Ветка

### Новая самостоятельная задача

1. Установи фактический remote из upstream текущей ветки; если upstream ещё нет,
   используй фактическое состояние `git remote -v`, а не предположение `origin`.
2. Определи ветку по умолчанию/base из удалённого состояния:

   ```powershell
   git ls-remote --symref $remote HEAD
   ```

3. Обнови базу безопасно.
4. Создай смысловую рабочую ветку. Имя отражает работу; номера PR, SHA, roadmap,
   stage/phase и локальные данные пользователя в имя не попадают.
5. Не подмешивай неизвестные пользовательские изменения.

### Продолжение существующей задачи

Продолжай существующую рабочую ветку и связанный PR. Новая ветка не создаётся
только потому, что работа получила новый подшаг или новый prompt.

### Ветка по умолчанию

Прямая разработка в ветке по умолчанию запрещена контрактом репозитория. Если
запрос конфликтует с этим инвариантом, назови конфликт и используй рабочую ветку
вместо молчаливого нарушения.

## 3. Verification и staging

1. Выполни применимые проверки от их фактического владельца:
   `.codex/context/verification.md` и профильные документы-владельцы затронутой
   области. Этот skill не копирует verification matrix.
2. Классифицируй фактический результат каждой существенной проверки:
   - `PASSED` — проверка выполнена успешно;
   - `FAILED` — проверка выполнена, но нашла отказ/дефект; выясни причину,
     исправь доступное в scope и повтори проверку, если это безопасно;
   - `BLOCKED` — проверку остановила зависимость от окружения, устройства,
     доступа или другого внешнего условия; не выдавай это за дефект кода;
   - `NOT_RUN` — проверка не выполнялась; укажи почему.
   Не выдавай `FAILED`, `BLOCKED` или `NOT_RUN` за `PASSED`. Сохрани
   применимые результаты и основания ограничений для PR body.
3. Просмотри итоговый diff целиком.
4. Добавь в индекс только пути текущей рабочей задачи:

   ```powershell
   git add -- @taskPaths
   ```

5. Перечитай staged diff:

   ```powershell
   git diff --cached --stat
   git diff --cached
   git status --porcelain
   ```

Случайные staged/untracked изменения пользователя не добавляются, не коммитятся
и не удаляются. `.codex/local/` не попадает в индекс. Если принадлежность
изменения задаче неясна, автоматический staging останавливается до разрешения
неоднозначности.

### Разделение блокеров проверки и публикации

При обычной задаче с ожидаемым PR не останавливай Git/GitHub lifecycle только
потому, что live/acceptance test завершился отказом, не смог подключиться к
устройству или не был запущен. То же относится к красной deterministic
verification: сначала исследуй и по возможности исправь причину, но не делай
успешность всех проверок предварительным условием самого Draft PR.

Если после обоснованных попыток исправления проверка остаётся `FAILED`,
`BLOCKED` или `NOT_RUN`, а подготовленный diff допустим к публикации,
выполни commit, push, проверь точный remote SHA и создай/обнови **Draft PR**.
Укажи в PR фактический результат каждой существенной проверки, причину,
непроверенное поведение и известные риски. Не объявляй реализацию полностью
проверенной, не переводи такой PR в Ready автоматически и не обходи CI/merge
gates. Не требуй отдельного повторного разрешения только из-за неуспеха теста,
если пользователь уже поручил обычную публикацию.

Публикацию останавливают только конкретные препятствия именно для безопасной
публикации: риск утечки секретов/закрытых данных, опасные или непонятные
посторонние изменения в индексе, невозможность однозначно установить
repository/branch/remote, явный запрет пользователя или другая подтверждённая
угроза самой операции. Не обходи эти препятствия и не подменяй отказ проверки
общим блокером без установления причины. При невозможности безопасной
публикации укажи причину и уже сохранённое состояние, не заявляя об успехе.

Проверочные сценарии для применения правила:

- live-test вернул `Absent` из-за недоступного устройства при безопасном diff
  → опубликованный Draft PR с `BLOCKED` и описанием environment gap;
- тест обнаружил воспроизводимый дефект, не устранённый в scope
  → Draft PR с `FAILED` и известным дефектом, не Ready;
- найден секрет в staged diff → публикация остановлена до устранения утечки;
- локальный commit уже создан после неуспешного теста → при отсутствии
  публикационного блокера обязательно продолжить push и PR.

## 4. Commit

- Commit описывает фактическое изменение.
- Сохраняй устойчивый conventional style репозитория, если он существует.
- Conventional prefix/scope остаются точными техническими идентификаторами;
  человеческая формулировка следует языковой политике проекта.
- В сообщение не попадают текущий PR number, SHA, roadmap/stage number и разовый
  план.
- Несвязанные локальные изменения не включаются.

Пустой commit не используется как способ «закрыть» задачу. Он допустим только
если отдельный реальный workflow явно владеет таким контрактом.

## 5. Push

Публикуй текущую рабочую ветку явно в ожидаемый remote/ref. Голый `git push`
не является контрактом skill, потому что зависит от локальной конфигурации Git.

Перед push прочитай удалённую ссылку. Если remote ref существует и расходится с
локальным состоянием, сначала fetch и исследуй расхождение; чужие commits не
перезаписываются.

```powershell
git ls-remote --refs $remote "refs/heads/$branch"

# первая публикация
git push --set-upstream $remote "refs/heads/${branch}:refs/heads/${branch}"

# последующая публикация
git push $remote "refs/heads/${branch}:refs/heads/${branch}"
```

Force-push не используется без отдельного явного основания.

## 6. Remote postcondition

Публикация подтверждена только при:

```text
ожидаемый локальный HEAD == фактический SHA соответствующей remote branch
```

Читай фактическую удалённую ссылку:

```powershell
git rev-parse HEAD
git ls-remote --refs $remote "refs/heads/$branch"
```

Remote-tracking ref сам по себе недостаточен: он может быть неактуальным.
Расхождение означает, что ожидаемое состояние не опубликовано.

## 7. Неизвестный результат сетевой операции

Если push или другая сетевая операция записи завершилась
таймаутом/обрывом/неясным ответом:

1. сначала прочитай фактическое удалённое состояние;
2. не повторяй операцию записи вслепую;
3. повторяй запись только если доказано, что ожидаемое изменение не применилось;
4. не перезаписывай новые чужие commits.

То же правило действует для create/edit PR: неизвестный результат сначала
разрешается чтением состояния GitHub. Второй PR для того же base/head — дефект.

## 8. Запрещено без отдельного текущего разрешения

- force-push;
- rebase/amend уже опубликованной истории;
- удаление неизвестных remote branches;
- публикация другой ветки вместо текущей рабочей задачи;
- публикация несвязанных локальных изменений;
- смена base/PR, закрытие PR или merge;
- обход обязательных checks/ревью административными или force-механизмами.

## 9. Завершённое состояние публикации

```text
staged diff соответствует задаче
commit создан в рабочей ветке
push выполнен явно в ожидаемый remote/ref
фактический remote SHA равен ожидаемому локальному HEAD
```

После этого переходи к [`pr-lifecycle.md`](pr-lifecycle.md).
