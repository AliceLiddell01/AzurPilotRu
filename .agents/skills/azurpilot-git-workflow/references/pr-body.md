# Описание PR

Этот файл владеет **содержательной структурой** PR body для
`azurpilot-git-workflow`. Источник body, публикация, повторное чтение,
Draft/Ready, merge и очистка принадлежат `pr-lifecycle.md`.

## 1. Главный принцип

Пиши для человека, который не читал чат и видит только PR. Body должен отвечать:

- зачем существует изменение;
- что именно изменилось;
- как это проверено;
- в каком состоянии CI и обязательное ревью;
- что ещё ограничивает готовность.

Project-owned проза следует `.codex/context/language.md`; точные имена API,
CLI, файлов, классов, команд, checks/jobs и идентификаторов сохраняются.

Body строится по **фактическому текущему состоянию** рабочей задачи. Не копируй
исходный prompt, стенограмму работы агента, полный журнал команд, временную
дорожную карту или старый снимок, который уже не соответствует HEAD.

## 2. Обязательная структура содержательного PR

Обычный содержательный PR использует реальные Markdown-заголовки второго уровня:

```text
## Цель
## Область изменений
## Реализация
## Проверки
## CI
## Готовность
## Ограничения
```

### `## Цель`

1–3 плотных предложения:

- какую проблему или capability закрывает PR;
- почему изменение нужно;
- какое наблюдаемое состояние должно быть после merge.

### `## Область изменений`

Кратко фиксируй фактическую границу:

- основные подсистемы/владельцы и типы артефактов;
- repository/base/head, когда это помогает проверке;
- base SHA/текущий HEAD, если они действительно нужны для исключения
  неактуальных подтверждений;
- важную границу вне scope только когда без неё область работы неочевидна.

Не превращай раздел в полный список файлов.

### `## Реализация`

Опиши существенные инженерные решения и причины:

- владельца поведения/данных;
- изменённый поток или контракт;
- важную семантику ошибок и восстановления;
- сохранённые архитектурные инварианты.

Пиши о результате, а не о последовательности действий агента.

### `## Проверки`

Указывай только фактически выполненные проверки и их результат. Для существенной
проверки должно быть понятно, что она доказывает. Недоступная или непройденная
проверка называется прямо; запланированная проверка не выдаётся за выполненную.

### `## CI`

Фиксируй проверки GitHub Actions относительно **текущего PR HEAD**:

- точный HEAD при необходимости;
- обязательные jobs/contexts и их состояние;
- `pending`, `NOT_RUN` или недоступность, если финального результата нет.

Зелёный CI предыдущего HEAD не считается подтверждением нового HEAD.

### `## Готовность`

Кратко укажи:

- завершена ли реализация;
- Draft/Ready state;
- состояние обязательных checks/ревью;
- что merge не выполнялся без отдельного разрешения пользователя.

### `## Ограничения`

Только реальные ограничения, риски, недоступные проверки или препятствия. Если
существенных ограничений нет, достаточно одной строки.

## 3. Условные разделы

Добавляй их только когда они применимы.

### `## Runtime-проверка`

Для реального end-to-end/runtime/device/browser acceptance, который существенно
сильнее статических tests. Опиши сценарий и наблюдаемый результат.

### `## Безопасность`

Когда задача затрагивает trust boundary, filesystem/network input, secrets или
когда выполнялся отдельный security/secret scan.

### `## Миграция и откат`

Для persistence/runtime/schema/config migrations, compatibility window,
recovery/rollback или другого переходного состояния.

### `## Внешнее ревью`

Только когда в текущей рабочей задаче фактически использован внешний ревьюер и у
него ещё нет отдельного владельца формата. Не создавай заранее таблицы, счётчики
итераций или правила обработки результатов, привязанные к конкретному провайдеру.

Если позже появится отдельный владелец ревью, он определяет, какие данные
содержательно должны быть сохранены; этот файл определяет только место и
читаемую форму их представления в PR body.

## 4. Плотность и читаемость

Обычно достаточно короткого абзаца или нескольких содержательных пунктов на
раздел. Не дублируй одно подтверждение в нескольких местах. Таблицы используй
только для действительно табличных данных.

## 5. Актуализация body

Body — живое описание PR.

При изменении фактов:

1. обнови локальный для репозитория источник body из `pr-lifecycle.md`;
2. перечитай полный файл;
3. опубликуй его;
4. перечитай опубликованный PR и сравни с источником;
5. после изменения HEAD обнови состояние CI/ревью только по подтверждениям нового
   HEAD.

Не сохраняй в body временную историю агента вместо текущего состояния продукта.
