# AzurPilotRu: жизненный цикл Git/GitHub обычной задачи

## Назначение

Skill — **единственный владелец** общей процедуры Git/GitHub для текущей рабочей
копии: рабочая ветка, индекс, commit, push, проверка удалённого состояния,
создание и обновление PR, содержательное описание PR, Draft/Ready, отдельно
разрешённый merge и очистка после merge.

Skill не владеет:

- содержанием инженерной работы: его определяют задача, `AGENTS.md`,
  `.codex/context/` и фактический код;
- набором и смыслом проверок репозитория — этим владеет
  `.codex/context/verification.md`;
- архитектурой, build/dependency contracts и языковой политикой — у них уже есть
  владельцы из `.codex/context/INDEX.md`;
- независимым code review;
- логикой конкретного внешнего reviewer, его CLI, findings, итераций и disposition.

Соподчинённость владельцев:

```text
azurpilot-git-workflow
    └─ ветка / индекс / commit / push / remote postcondition /
       создание и обновление PR / PR body / Draft+Ready /
       разрешённый merge / конфликты / cleanup

.codex/context/verification.md
    └─ какие проверки применимы и что именно они доказывают

будущий code-review skill
    └─ содержательное независимое review без подмены Git lifecycle

будущий внешний reviewer skill
    └─ только процедура конкретного провайдера, если такая capability появится
```

Не создавай второго владельца общей Git/GitHub-процедуры в `AGENTS.md`,
`.codex/context/` или будущих review-skills. Не вводи собственную обёртку над
`git`/`gh`, state machine или журнал публикации без отдельной доказанной
потребности.

## Контракт маршрутизации

Skill применяется по намерению, а не по буквальному имени:

- создание или продолжение рабочей ветки;
- staging;
- commit;
- push;
- создание или обновление PR;
- Draft/Ready;
- проверка удалённого состояния перед передачей результата;
- разрешение конфликтов с base;
- отдельно разрешённый merge;
- cleanup после merge;
- продолжение уже начатой публикации.

Явные запросы «закоммить», «запушь», «создай PR», «обнови PR», «сделай Draft
PR», «переведи PR в Ready», «слей PR» маршрутизируются сюда же.

Skill не активируется для:

- объяснения Git/GitHub без mutations;
- read-only исследования истории, веток или PR;
- независимого code review;
- запуска или анализа конкретного внешнего reviewer;
- задачи по изменению самого skill как повода выполнить дополнительные GitHub
  actions сверх явно текущего work item.

## Контракт конечного состояния: commit не равен публикации

Если задача предполагает публикацию результата и пользователь явно не ограничил
её локальной работой, состояние

```text
есть новый локальный commit
удалённая ветка его не содержит
```

**не является** завершением.

Обычная публикуемая задача проходит цепочку:

```text
изменение
→ применимые проверки от их владельца
→ проверенный индекс
→ commit
→ push текущей task branch
→ точное чтение удалённого HEAD
→ создание или актуализация Draft PR
→ повторное чтение опубликованного PR
→ передача результата пользователю
```

Merge в автоматический lifecycle не входит. Он выполняется только по отдельной
текущей явной команде пользователя.

Явное «только локально», «только commit» или «не push» ограничивает цепочку
ровно настолько, насколько сказано, и только для текущего поручения.

Публикация подтверждена не exit code команды, а равенством ожидаемого локального
HEAD фактическому SHA соответствующей remote branch. Подробности принадлежат
[`references/publication.md`](references/publication.md).

## Штатные инструменты

- `git` — локальная история, status/diff, ветки, staging, commit, fetch,
  разрешённая синхронизация с base, push и чтение remote refs;
- `gh` — создание/обновление PR, Draft/Ready и отдельно разрешённый merge;
- GitHub connector — предпочтительное структурированное чтение GitHub state,
  когда доступен; удалённые mutations через него выполняются только когда
  текущая среда действительно работает через connector и пользователь разрешил
  соответствующее действие;
- `gh ... --json` — допустимый fallback для структурированного чтения.

Версионно-зависимые flags и поля CLI не являются вечным контрактом: проверяй
фактический интерфейс установленной версии там, где это необходимо.

## Инварианты

- Одна самостоятельная задача — одна task branch и один PR.
- Не работай напрямую в default branch.
- Ветки не переключаются молча.
- Не считай локальный commit доказательством публикации.
- Не считай успешный push доказательством конечного remote state без чтения
  фактической удалённой ссылки.
- Разрешение на commit/push не разрешает merge.
- Не создавай дублирующий PR для того же repository/base/head.
- Не хардкодь номер PR, имя ветки, SHA, номер roadmap/stage, абсолютный локальный
  путь или имя пользователя как постоянный контракт.
- Не подмешивай и не уничтожай неизвестные пользовательские изменения.
- Merge, force-push, переписывание опубликованной истории и удаление неизвестных
  remote branches требуют отдельного явного основания в текущем запросе.
- Не ослабляй применимые проверки и не подменяй их владельца.
- После изменения HEAD ранее полученные CI/review evidence считаются stale, пока
  не доказано обратное для нового HEAD.
- Не вводи review-инфраструктуру «на будущее»: отдельный review owner появляется
  вместе с реальной capability.
