# План, свидетельства и завершение

До прогона сохрани компактную матрицу: capability → production path → предусловия → ожидаемый результат
из владельца → независимое evidence → отрицательный сценарий → разрешённое восстановление/конечное состояние.
Включи все существенно затронутые пути. Если путь неприменим, обоснуй это до запуска.
Ожидания не вычисляются из ответа проверяемой реализации и не меняются под фактический результат.

## Связь с исходниками

Запиши HEAD, dirty diff, конфигурацию сборки, команду и результат штатной сборки, путь и SHA-256 EXE,
App DLL и применимой native DLL. Проверь, что запускается именно этот файл, а не другой PATH/worktree.
Если бинарник меняется, начни новую проверку с новой identity сборки. Версии среды и хеш изолированного
конфига сохраняй локально; не публикуй полный пользовательский YAML или machine-specific пути.

## Вызов и независимая проверка

Собирай exit code **самого CLI**, raw stdout и отдельный stderr через pipes без ConPTY. Проверь один
UTF-8 JSON без BOM/баннера/VT, отсутствие хвостового второго документа, `schemaVersion` и bounded size
по текущему AgentJson/discovery. Не превращай stderr в пустой вывод ради успеха.

Для каждого ответа сравни `operation`, `requestedTarget`/`target`, `exitCode`, `status`, `failure`,
`effect`, `data` с заранее заданным контрактом. Независимое наблюдение состояния, новый capture,
реальные размеры/метрики/идентичность процесса подтверждают исполнение пути; `success`/код 0 и
завершение обёртки сами по себе недостаточны. Лог — вспомогательное evidence, не единственный assertion.
Ошибку помощника отделяй от доказанного дефекта продукта.

`none`, `changed`, `mayHaveChanged` имеют семантику [Agent CLI](../../../../docs/reference/agent-cli.md).
Сохраняй partial effects, последние наблюдения, nullable facts и `data.completed` при ошибке shutdown.
Изменившийся ADB transport не доказывает переход игры. Timeout помощника не должен бросать незавершённую
mutation и освобождать её аренду: учитывай production probe/postflight/shutdown tail, не увеличивай
лимиты без причины и не убивай чужие процессы. Принудительный выход не доказывает rollback или JSON.

## Debug-отчёт PR-приёмки

Контракт и состав отчёта — [Agent CLI Debug Mode](../../../../docs/reference/agent-cli.md#debug-mode).
Для приёмки PR:

- Все вызовы прогона, включая preflight, cleanup и отрицательные сценарии, получают один и тот же
  `--debug-report pr-<n>-<slug>`; рабочий каталог — проверяемый checkout. До записи —
  `git check-ignore -v .codex/local/reports/<session>/x`, после — `git status` без новых файлов.
- После каждого вызова прочитай stderr-строку `AzurPilot.App.Agent.Debug` и `manifest.json`:
  `state=completed`, `diagnostics.status`, `incompleteReasons`, `run.correlationId` = correlationId
  envelope, `counters.captured` = `counters.rendered` + skipped/failed/dropped с причинами.
  `incomplete` — ограничение evidence (PARTIAL для требования отчёта), а не исход команды.
- Сверь фактические `frameId` envelope с `manifest.frames`, а события `tap_*`/`postcondition_frame`
  в `trace.jsonl` — с ожидаемым flow. Просмотри JPEG кадров решений локально; их содержимое, UID,
  чаты и скриншоты не копируются в PR, CI, сообщения и отчёты.
- Измерь накладные расходы: тот же сценарий и стартовое состояние с флагом и без (не меньше чем по
  одной выборке каждого; для игровых mutation — по правилам повторных performance-прогонов ниже).
  Сравнивай wall-clock и производственные тайминги envelope; диагностическую работу бери из
  `performance.json`. Прогон без флага не создаёт отчёт — проверь это по каталогу сессии.
- Debug Mode не меняет авторизацию: разрешения на mutation, target и cleanup остаются прежними.

## Mutation и cleanup

Перед действием сверь текущее разрешение пользователя, identity, отсутствие конкурирующего внешнего
управления и повторные наблюдения. Авторизация подготовки transport не разрешает запуск MuMu/игры;
разрешение запуска не разрешает игровой tap. При Unknown/неоднозначности остановись fail closed.
Флаг mutation в discovery — характеристика операции, а не согласие пользователя.

Восстановление выполняй production-командой только в разрешённых пределах и при доказанной
принадлежности изменения этому прогону. Подтверди итог отдельным наблюдением. Если исходное или
текущее состояние недоказано, сохрани неопределённость и запроси конкретное решение; не останавливай
«для чистоты» уже работавшую чужую среду. Не чисти lock-файлы WindowsInstanceMutationLease.

## Игровые capabilities

- Live-приёмка игрового запуска, foreground, движущихся кадров, ввода, загрузки, latency и game-ready
  выполняется только на проверенном exact MuMu с установленной игрой. Unit/contract/CTest, PNG-фикстуры,
  статические сканы и replay называются deterministic/offline, не `live PASS`.
- Автономная capability запускается одним production-триггером (например,
  `agent game-ui-ready-ensure --target <identity>`). Помощник измеряет wall-clock, читает bounded
  JSON/stdout/stderr и выполняет отдельные read-only postconditions; цепочка «ручной tap → снимок →
  tap», fake JSON, mock ADB и собственная логика игровых решений не являются приёмкой.
- Фазы и стоимость берутся из телеметрии production envelope. Невстреченная или ненаблюдаемая фаза —
  `NOT_TESTED`/`UNKNOWN`; успешный ADB/foreground не доказывает главный UI.
- Новая или изменённая игровая mutation-capability считается проверенной по производительности только
  с собственной измеренной live-latency на MuMu по шагам (wall-clock, каждый переход, захваты,
  viewport, ввод, момент кадра-доказательства), сопоставимой с baseline в тех же условиях; зелёный
  `changeProven` её не заменяет.
- Конечное состояние согласованного игрового прогона: штатный `game-stop` только Azur Lane,
  независимые `game-observe → Stopped` и `mumu-observe → Running` с пригодным transport, тот же exact
  target. `mumu-stop`, `mumu-restart`, закрытие player.exe и остановка ADB-сервера как cleanup запрещены;
  неожиданно завершившийся MuMu — отдельный FAIL без скрытого рестарта.
- Запуск исходно Stopped MuMu и оставление его Running, остановка уже работавшей до теста игры —
  только в явно согласованных границах; иначе `BLOCKED` без mutation. Финальный `game-stop` — после
  подтверждения identity и доступности Android; при недоказанном состоянии или `mayHaveChanged` слепой
  компенсирующий stop не выполняется, а blocker фиксируется. Успех stop без наблюдения `Stopped` не PASS.
- Повторные performance-прогоны используют тот же работающий MuMu: штатный старт игры → один
  автономный цикл → проверка итога → `game-stop` и доказанный `Stopped` → следующий старт. Cold start
  игры, warm Ready и отдельные capture/viewport сравниваются раздельно, с числом выборок, медианой и
  разбросом; прогоны из разных стартовых состояний не сравниваются как выигрыш оптимизации.
- Не провоцируй logout, покупки, обновления, награды или изменение аккаунта ради покрытия.

## Статусы

| Статус | Значение |
| --- | --- |
| PASS | Все ожидания данного сценария и независимые postconditions доказаны |
| FAIL | Исполненный путь нарушил заранее заданный контракт |
| PARTIAL | Запуск состоялся, но существенное свидетельство/конечное состояние или причина отказа не установлены |
| NOT_RUN | Сценарий не запускался; указана причина, включая отсутствие разрешения |
| BLOCKED | Подтверждённая внешняя предпосылка препятствует проверке; указаны первый блокер и доступные факты |

Намеренно негативный PASS доказывает только ожидаемый отказ и сохранение postconditions, а не штатную
успешную операцию. Нельзя удалять неудобные строки матрицы после запуска. Итоговый PASS требует PASS
каждого обязательного сценария; иначе перечисли фактические статусы без общего зелёного вывода.

В отчёте укажи сборку, сценарий, команду, статус, независимое evidence, проверку cleanup и ограничения.
Deterministic/CI/real-device evidence различаются по
[verification](../../../../.codex/context/verification.md). Проверь Git status и ignored boundary;
разовые помощники не становятся постоянной инфраструктурой вследствие единственного запуска.
