# Пользовательская конфигурация приложения — подробная документация

Этот документ сохраняет развёрнутое описание текущего устройства, rationale, примеры и evidence.
Короткий agent-critical contract находится в
[.codex/context/application-configuration.md](../../.codex/context/application-configuration.md).
Фактическое состояние production-кода, tests и manifests имеет приоритет над устаревшей prose-документацией.

## Роль конфигурации

Конфигурация приложения — строгий типизированный пользовательский документ, который application host
загружает один раз при запуске. Screenshot diagnostics не добавляет пользовательских настроек. Секции
для input, keymap, разрешения экрана и OCR в схему не добавляются: секция появляется вместе с реальным
пользовательским решением, которое нужно конфигурировать, а не заранее. Секция `mumu` содержит ровно одну
реальную настройку — выбор Android-экземпляра. Product identity игры (регион/сервер/пакет) настройкой
конфигурации не является: поддерживается ровно один клиент — Azur Lane Global/EN, чья identity
принадлежит владельцу [android-game-lifecycle.md](../architecture/android-game-lifecycle.md), а не пользовательскому
документу. По той же причине в схеме нет ключей вида `adb.*` и `game.*`: точный ADB endpoint и product
identity — runtime-данные реализованной capability, а не настройки оператора.

## Runtime-пути

Владелец путей — `AzurPilotConfigurationPath` в `src/AzurPilot.Core/Configuration/`. Оба пути
вычисляются через BCL API (`Environment.SpecialFolder.LocalApplicationData`), а не хранятся строками:
абсолютный путь конкретной машины в репозитории запрещён
([architecture.md](../architecture/overview.md)).

| Метод владельца | Путь | Роль |
| --- | --- | --- |
| `GetDefaultRuntimePath()` | `%LOCALAPPDATA%\AzurPilot\config.yaml` | Каноническая конфигурация схемы v3 |
| `GetLegacyJsonRuntimePath()` | `%LOCALAPPDATA%\AzurPilot\config.json` | Legacy-вход схем v1 и v2 |

Приложение не создаёт каталог конфигурации и не пишет файл при запуске: отсутствие каталога или файла —
валидный сценарий запуска, а не ошибка. Создание `config.yaml` требует явного сохранения настроек
или миграции (см. ниже). Startup вычисляет runtime-путь через владельца путей; CLI позволяет выбрать
режим интерфейса, но не подменить путь. Явно переданные пути существуют только как код-параметр composition — это
seam, которым тесты указывают временные файлы, не подменяя пользовательскую конфигурацию.

## Эффективная схема v3

Версия схемы, которую понимает текущая сборка, принадлежит константе
`AzurPilotConfiguration.CurrentSchemaVersion`; загрузчик, встроенные defaults, запись канонического YAML
и тесты используют её, а не собственную копию числа. Номера legacy-схем принадлежат их контрактам:
`AzurPilotConfigurationV1.LegacySchemaVersion = 1` и `AzurPilotConfigurationV2.LegacySchemaVersion = 2`.

Полный проверенный канонический документ:

```yaml
schemaVersion: 3
ui:
  mode: normal
mumu:
  instance: "mumu:1"
diagnostics:
  minimumLevel: Information
logging:
  viewer:
    enabled: false
```

### Ключи схемы

| Ключ | Обязателен | Тип и допустимые значения | Значение по умолчанию |
| --- | --- | --- | --- |
| `schemaVersion` | да | целое число без кавычек; поддерживается только `3` | — |
| `ui` | да | блочный mapping | — |
| `ui.mode` | да | строка: `normal`, `manual`, `diagnostic` (только нижний регистр) | — |
| `mumu` | да | блочный mapping | — |
| `mumu.instance` | нет | строка: литерал `auto` либо `mumu:<digits>` | `auto` |
| `diagnostics` | да | блочный mapping | — |
| `diagnostics.minimumLevel` | нет | строка — точное имя `LogLevel` | `Information` |
| `logging` | да | блочный mapping | — |
| `logging.viewer` | да | блочный mapping | — |
| `logging.viewer.enabled` | да | булево: ровно `true` или `false` без кавычек | — |

Смысл ключей:

- `schemaVersion` — версия схемы документа. Документ без него невалиден, а значение, отличное от `3`,
  означает неподдерживаемую схему;
- `ui.mode` — режим запуска операторского интерфейса: `normal` содержит только пользовательские операции,
  `manual` добавляет ручное управление отдельными операциями, `diagnostic` — полный технический
  инструментарий. Перечень строк выводится из имён `OperatorUiMode`, поэтому второй копии допустимых
  значений нет;
- `mumu.instance` — выбор Android-экземпляра. Допустимы ровно две формы: литерал `auto` (экземпляр
  выбирает провайдер) и провайдерская форма `mumu:<digits>`, например `mumu:1`, где `<digits>` —
  неотрицательное целое без ведущих нулей и без знака. Всё остальное — пустая строка, display name, `1`,
  `mumu:`, `mumu:01`, `mumu:-1`, нестроковый тип — несоответствие схеме. Синтаксис значения принадлежит
  единственному владельцу `MuMuInstanceValue` в `src/AzurPilot.Core/Configuration/`, а строгий YAML-ридер
  и строгий JSON-конвертер legacy-документов только вызывают его: второй копии грамматики нет.
  **Отсутствие ключа означает `auto`**;
- `auto` не является «выбором первого попавшегося экземпляра»: разрешение выбора принадлежит
  `AzurPilot.Core.MuMu` и при нуле подходящих экземпляров сообщает «не найден», а при двух и более —
  «неоднозначен». Тихий выбор первого или последнего экземпляра не выполняется;
- `diagnostics.minimumLevel` — минимальный уровень логирования, попадающий в structured runtime logs.
  Допустимые имена — это имена типа `LogLevel` из logging stack, поэтому Core не хранит вторую копию их
  перечня. Числовая форма, неизвестное имя и произвольный регистр отвергаются;
- `logging.viewer.enabled` — включает отдельный просмотрщик журнала. Настройка **не дублирует**
  минимальный уровень: уровень определяет, что вообще попадает в журнал, а просмотрщик — только
  отображение уже записанного;
- имена ключей заданы явно в camelCase и совпадают с именами JSON-свойств legacy-контрактов: второй
  перечень имён не заводится;
- метаданные JSON-типов приходят из source-generated контекста; reflection-based десериализация
  конфигурации не используется.

Example-config в репозитории не создаётся: он стал бы вторым владельцем тех же значений, который
пришлось бы синхронизировать с defaults отдельными проверками.

### Значения по умолчанию

Встроенные значения по умолчанию существуют ровно в одном месте — `AzurPilotConfigurationDefaults` в
`src/AzurPilot.Core/Configuration/`. Сценарий «файла нет», нормализация legacy-входа и чтение YAML
обращаются туда. Ридер YAML строит результат поверх этих defaults и переопределяет только явно заданные
ключи, поэтому необязательные ключи не дублируют значения по умолчанию.

| Ключ | Встроенное значение |
| --- | --- |
| `ui.mode` | `normal` |
| `mumu.instance` | `auto` |
| `diagnostics.minimumLevel` | `Information` |
| `logging.viewer.enabled` | `false` |

Встроенная конфигурация описывает ту же схему v3, что и канонический файл, поэтому проходит те же
проверки.

### Пустая секция

Секция без вложенных ключей (`mumu:` или `diagnostics:` без значения) — это YAML null. Такая запись
означает «ни один ключ секции не задан»: она читается как пустая секция, после чего отсутствие
обязательных ключей сообщается отдельным отказом. Секция со скалярным значением (`mumu: auto`) —
неверный тип и отказ.

## Строгость YAML

Владелец разбора — `AzurPilotYamlConfigurationReader` в `src/AzurPilot.Core/Configuration/`: документ
разбирается низкоуровневыми событиями `YamlDotNet` (`IParser`), а не десериализацией в объект. Пакет
даёт синтаксис YAML; правила схемы остаются в Core. Гарантии:

- корень — блочный mapping; ключом может быть только скаляр;
- ровно один документ в потоке: multi-document и явный маркер `---` — отказ;
- неизвестный ключ на любом уровне, включая секции будущих capability, — отказ;
- повторяющийся ключ в любой секции — отказ;
- отсутствие обязательного ключа — отказ;
- anchor (`&`), alias (`*`) и tags (`!!`) — явный отказ;
- flow-стиль (`{...}`, `[...]`) и последовательности — отказ;
- merge-key `<<` — отказ;
- неверный YAML-синтаксис — отказ с понятным сообщением;
- `schemaVersion`, отличный от `3`, — отказ `configuration_schema_unsupported` с версией в details.
  Версия читается до строгой проверки секций, поэтому документ будущей схемы получает именно этот отказ,
  а не сообщение о неизвестном ключе;
- неверный тип значения — отказ: `ui.mode` не строка, `logging.viewer.enabled` не булево, `schemaVersion`
  не целое число без кавычек;
- `ui.mode` принимается строго как `normal`/`manual`/`diagnostic` в нижнем регистре: `Normal`, `NORMAL`,
  `mode: 1` и любое иное значение — отказ;
- `logging.viewer.enabled` принимается строго как литералы `true` и `false`: `"true"` (строка), `True`,
  `yes`, `1` — отказ;
- `mumu.instance` проверяет владелец грамматики: отрицательные, числовые и прочие формы дают
  детерминированный отказ;
- пустой файл и файл из одних комментариев — отказ «не содержит документа»;
- файл читается как UTF-8; ведущий BOM допускается, потому что относится к кодировке файла, а не к
  документу. Строгость при этом не ослабляется: BOM не делает невалидный документ валидным, а
  некорректная кодировка — отказ, а не чтение с подстановкой символов;
- блок-скаляры (`|`, `>`) для строковых ключей — отказ: значение должно быть обычной строкой.

Отклонения в сторону строгости осознанны и зафиксированы в XML-doc типов. Строка значений схемы
записывается в кавычках там, где plain-форма изменила бы смысл (например `instance: "mumu:1"`).

## Правила загрузки

Владелец — `AzurPilotConfigurationLoader`:

| Операция | Назначение |
| --- | --- |
| `Load(string path)` | Явный один файл; формат определяется расширением |
| `LoadRuntime()` | Runtime-политика по обоим путям владельца путей |
| `LoadFromSources(string canonicalPath, string legacyJsonPath)` | Та же политика с явными путями: код-параметр composition и seam для проверок |

`Load` определяет контракт по расширению:

- `.yaml`/`.yml` — строгий разбор YAML эффективной схемы v3;
- `.json` — строгий legacy-контракт v1 или v2 с нормализацией к v3 в памяти. JSON-документ v3 не
  существует, поэтому `schemaVersion: 3` в JSON-файле — неподдерживаемая схема;
- любое другое расширение — отказ `configuration_invalid`.

Общие правила:

- отсутствие файла или каталога — успешная загрузка встроенных defaults схемы v3; файл при этом не
  создаётся;
- существующий файл читается полностью и валидируется контрактом своей версии; невалидный файл никогда
  не подменяется defaults, а даёт явный отказ;
- существующий, но нечитаемый файл — тоже отказ, а не defaults: иначе сбой чтения выглядел бы как
  отсутствие конфигурации;
- относительный, пустой или состоящий из пробелов путь — ошибка программирования вызывающей стороны
  (исключение), а не ожидаемый отказ загрузки;
- конфигурация читается один раз: автоматического file watcher и reloadOnChange нет.

Snapshot — `AzurPilotConfigurationSnapshot`: immutable конфигурация вместе с источником
(`BuiltInDefaults` или `File`), форматом (`None`, `Yaml`, `Json`), путём файла и обеими версиями схемы —
версией, которую объявил источник, и версией эффективной схемы (для встроенных defaults они совпадают).
Создать snapshot вручную нельзя, поэтому snapshot всегда провалидирован, а изменение или удаление файла
после загрузки на него не влияет.

## Политика двух источников

`LoadRuntime()` и `LoadFromSources(...)` применяют одну и ту же детерминированную политику:

| Состояние | Результат |
| --- | --- |
| Существует только `config.yaml` | Загружается канонический YAML схемы v3 |
| Существует только `config.json` | Legacy-документ читается строго и нормализуется к v3 **в памяти** |
| Существуют оба файла | Отказ `configuration_invalid` с обоими путями в details и инструкцией по миграции |
| Нет ни одного файла | Встроенные defaults схемы v3 |

Настройки двух источников **не смешиваются по ключам** и ни один из файлов не выбирается автоматически:
решение о переносе принимает оператор. Отказ называет канонический путь в `config_path`, legacy-путь в
`legacy_config_path` и объясняет, что нужно сделать. Автоматической миграции при загрузке нет.

## Legacy-вход JSON и нормализация в памяти

Документ `schemaVersion: 1` (только секция `diagnostics`) и документ `schemaVersion: 2` (секции
`diagnostics` и `mumu`) допускаются как legacy-вход. Каждый читается строгим контрактом своей версии и
нормализуется к эффективной схеме v3 **в памяти**:

- прочитанные значения сохраняются, а ключи, которых в legacy-схеме не было (`ui.mode`,
  `logging.viewer.enabled`, для v1 — ещё и `mumu.instance`), приходят от владельца встроенных defaults;
- нормализация существует только в памяти: файл не перезаписывается, не создаётся и не ремонтируется;
- строгость не ослабляется: секция `mumu` для контракта v1 — неизвестное свойство, поэтому документ v1
  с ней невалиден, как и любой другой документ, не соответствующий своему контракту;
- нормализация не делает валидным невалидный документ;
- snapshot несёт и версию схемы источника, и версию эффективной схемы, поэтому нормализованный
  legacy-вход отличим от канонического YAML без дампа конфигурации.

Legacy JSON не является вторым равноправным форматом: он поддерживается для чтения и явной миграции, а
каноническая запись существует только в YAML.

## Контролируемая миграция legacy JSON в YAML

В TUI откройте «Настройки» → «Сохранить YAML / перенести legacy JSON с резервной копией».
Выбор точного экземпляра и изменение режима или viewer используют тот же `AzurPilotConfigurationStore`:
кандидат сначала проверяется loader-ом, затем сохраняется атомарно. При существующем YAML остаётся
backup прежних байтов; при legacy JSON выполняется описанная ниже миграция. Путь фактического backup
показывается в результате. Изменённый извне источник требует перезапуска перед сохранением.

Сохранение не заменяет DI snapshot текущего host. Настройки режима и viewer вступают в силу после
перезапуска. Одновременно существующие YAML и JSON сначала требуют устранить конфликт: меню
не выбирает один из источников за пользователя. Входной документ ограничен 64 КиБ.

Владелец — `AzurPilotConfigurationMigration`:

| Операция | Назначение |
| --- | --- |
| `MigrateLegacyJsonToYaml(string legacyJsonPath, string yamlPath)` | Перенос по явным путям |
| `MigrateRuntimeLegacyJsonToYaml()` | Тот же перенос по путям владельца путей |

Миграция выполняется **только по явному действию оператора** и никогда не запускается при загрузке
конфигурации. Порядок шагов фиксирован:

1. legacy JSON читается прежним строгим контрактом своей версии — невалидный файл не мигрируется;
2. канонический YAML записывается атомарно: сначала во временный файл в том же каталоге, затем
   `File.Move` без замены существующего файла, поэтому чужой YAML не перезаписывается; каталог
   создаётся при необходимости;
3. записанный YAML повторно читается загрузчиком и сверяется с ожидаемым snapshot;
4. только после успешной проверки legacy-файл **перемещается** в резервную копию
   `config.json.bak-<UTC timestamp>`: перемещение и есть backup, отдельного копирования нет;
5. любая неудача на шагах записи, проверки или перемещения возвращает состояние «существует только
   legacy JSON»: записанный YAML удаляется, а legacy-файл остаётся нетронутым.

Итог успешной миграции — ровно один действующий источник (`config.yaml`) плюс резервная копия
legacy-документа, поэтому runtime-политика «оба файла существуют» после миграции не срабатывает, и
оператор одним действием получает рабочее состояние. Существующий `config.yaml` не перезаписывается:
миграция отказывает, потому что решение о замене действующей конфигурации принимает оператор.

Результат — `AzurPilotConfigurationMigrationResult`: подтверждённый snapshot канонического YAML и путь
резервной копии, который операторский интерфейс обязан показать пользователю. Отказы возвращаются
значением `ApplicationResult<T>`; исключением сообщается только ошибка программирования вызывающей
стороны (пустой или относительный путь).

## Отказы конфигурации

Стабильные коды отказа, соответствие «ситуация → код», признак повторяемости, состав details и коды
выхода процесса принадлежат [application-failures.md](application-failures.md): второй перечень здесь
не заводится.

Правила этого документа:

- отсутствие файла или каталога конфигурации отказом не является — загрузка успешна на встроенных
  defaults;
- существующий файл, который не читается или не соответствует схеме своей версии, напротив, никогда не
  подменяется defaults и даёт явный отказ;
- конфликт двух источников — тоже `configuration_invalid`, а не новый код: это несоответствие
  пользовательской конфигурации, а не отдельная capability;
- отказы конфигурации не помечаются retryable: файл должен исправить оператор, а повтор той же загрузки
  без изменения файла ничего не изменит.

## Границы capability

- Конфигурация не собирается из нескольких источников: `Microsoft.Extensions.Configuration` не
  агрегирует пользовательскую конфигурацию, а строгий snapshot передаётся в DI как готовый объект
  ([runtime-diagnostics.md](../operations/runtime-diagnostics.md)).
- Hot reload, `config reload`, продуктовая опция выбора пути к файлу конфигурации, example-config и
  автоматический repair/update конфигурации не вводятся. Миграция — отдельная явная операция.
- Диагностика сообщает о конфигурации bounded сведения (источник, версия схемы, статус валидации,
  минимальный уровень логирования) и не печатает полный документ; состав диагностического snapshot
  принадлежит [runtime-diagnostics.md](../operations/runtime-diagnostics.md).
