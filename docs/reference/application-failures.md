# Application-level модель отказов — подробная документация

Этот документ сохраняет развёрнутое описание текущего устройства, rationale, примеры и evidence.
Короткий agent-critical contract находится в [application-failures.md](../../reference/application-failures.md).
Фактическое состояние production-кода, tests и manifests имеет приоритет над устаревшей prose-документацией.

## Зачем нужен отдельный уровень отказов

Ожидаемый отказ приложения описывается значением, а не исключением: `ApplicationFailure` в
`AzurPilot.Core.Failures` отделяет machine-stable код от человекочитаемого сообщения, поэтому
потребитель опирается на код, а не разбирает текст исключения. Отдельная модель нужна и потому, что
исключения платформенной и native boundary (`AzurPilot.Windows`) остаются типизированными деталями
границы, а на application boundary операция представлена application-level результатом.

`ApplicationResult` и `ApplicationResult<T>` возвращают успех или ожидаемый отказ значением.
Исключением сообщается только ошибка программирования вызывающей стороны (например, пустой или
относительный путь конфигурации), а не ожидаемый отказ операции.

## Стабильные коды

Коды отказа принадлежат константам `ApplicationFailure` в `src/AzurPilot.Core/Failures/` — это
единственный владелец их значений, и второй перечень кодов в документации или коде не заводится.
Контракт закрыт: допустимы только коды реально существующих capability, а каталог под отсутствующие
подсистемы (ввод, screenshot, vision, OCR, gameplay, готовность UI и подобные) не создаётся. Новый код
появляется вместе с реализацией capability, которая его порождает, — здесь, в таблице ниже, и в
константах `ApplicationFailure` одновременно.

| Код (константа `ApplicationFailure`) | Когда возникает | Повтор |
| --- | --- | --- |
| `ConfigurationInvalid` | Существующий файл конфигурации не читается или не соответствует своей схеме; условия и поддерживаемые версии схем принадлежат [application-configuration.md](../../reference/application-configuration.md) | не имеет смысла |
| `ConfigurationSchemaUnsupported` | Версия схемы в файле не поддерживается этой сборкой | не имеет смысла |
| `NativeUnavailable` | Native библиотека отсутствует или не загружается | имеет смысл после восстановления native runtime |
| `NativeIncompatible` | Native библиотека загружена, но её ABI несовместим с ожидаемым | не имеет смысла без пересборки |
| `MuMuInstallationNotFound` | Установка MuMuPlayer не обнаружена: ни один источник не подтвердил её существование | имеет смысл после установки или починки установки |
| `MuMuInstallationAmbiguous` | Обнаружено несколько установок MuMuPlayer, а доказуемого правила выбора между ними нет | не имеет смысла без устранения лишней установки |
| `MuMuInstanceNotFound` | Среди Android-экземпляров установки нет ни одного, удовлетворяющего выбору | имеет смысл после создания экземпляра |
| `MuMuInstanceAmbiguous` | Автоматический выбор не разрешается: подходящих экземпляров несколько | не имеет смысла без явного выбора экземпляра |
| `MuMuControlSurfaceUnsupported` | Найденная установка не предоставляет поддерживаемую control surface либо её форма не распознана | не имеет смысла без другой установки или версии |
| `MuMuLifecyclePostconditionNotMet` | Mutation выполнена с ненулевым кодом выхода, а состояние не наблюдается | имеет смысл после устранения причины |
| `MuMuLifecycleTimeout` | Требуемое состояние экземпляра не доказано наблюдением в пределах deadline операции | имеет смысл: состояние могло измениться позже |
| `AndroidAdbUnavailable` | Bundled ADB обнаруженной установки недоступен: executable не найден, не запускается или форма ответа команды версии не распознана | не имеет смысла без починки установки |
| `AndroidEndpointUnavailable` | Точный ADB endpoint выбранного экземпляра не разрешён: сведения установки не содержат пригодного адреса, либо команда чтения сведений не уложилась в свой дедлайн | не имеет смысла, пока установка не сообщает точный адрес |
| `AndroidTransportNotReady` | ADB transport точного target-а не стал готов к командам в пределах границы ожидания | не имеет смысла без внешнего изменения состояния target-а |
| `AndroidNotReady` | Готовность Android на точном endpoint-е не доказана: shell недоступен или загрузка не завершена в пределах deadline | имеет смысл: готовность могла наступить позже |
| `AzurLanePackageMissing` | Устройство подтвердило отсутствие пакета игры на точном endpoint-е | не имеет смысла без установки пакета |
| `AzurLaneStateUnknown` | Состояние игры не доказано наблюдением, поэтому переход не выполняется | не имеет смысла, пока наблюдение не даёт распознанного ответа |
| `AzurLaneLauncherUnresolved` | Launcher-компонент пакета не разрешён: компонента нет либо запрос не дал распознанного ответа | имеет смысл после устранения причины |
| `AzurLaneLauncherAmbiguous` | Launcher-компонент неоднозначен: подходящих компонентов несколько, а запуск адресуется одному | не имеет смысла без устранения неоднозначности |
| `AzurLaneLifecyclePostconditionNotMet` | Mutation игры выполнена с ненулевым кодом выхода, а требуемое состояние не наблюдается | имеет смысл после устранения причины |
| `AzurLaneLifecycleTimeout` | Требуемое состояние игры не доказано наблюдением в пределах deadline операции | имеет смысл: состояние могло измениться позже |
| `OperationCancelled` | Операция отменена запросом отмены | решает вызывающая сторона |
| `InternalError` | Ошибка вне ожидаемых отказов выше | не имеет смысла |

Правила конфигурации, при которых возникают два первых кода, описаны в
[application-configuration.md](../../reference/application-configuration.md).

Отсутствие установки и её неоднозначность — разные случаи и разные коды: `MuMuInstallationNotFound`
утверждает, что установки нет, и не сообщается, когда установок несколько. Неоднозначность установки
симметрична неоднозначности экземпляра: оба случая означают «выбор не разрешён», а не «ничего не
найдено». Различие наблюдаемо по коду, поэтому потребителю не нужно разбирать текст сообщения.

## Признак повторяемости

`IsRetryable` — часть контракта отказа, а не подсказка presentation-слою: значение по умолчанию —
`false`, а `true` ставится только там, где повтор той же операции действительно может измениться
(например, временная недоступность native библиотеки). Код отказа и признак повторяемости
согласованы: отказ, который не изменится без внешнего действия оператора, не помечается retryable.

## Structured details

`Details` — необязательный ограниченный словарь «ключ → значение»: immutable, с ordinal-сравнением
ключей, равенство отказа включает его содержимое. Details предназначены для structured logging, а не
для пересказа сообщения: в них попадают только те данные, которые нужны потребителю для диагностики,
и никогда — полный документ конфигурации, полный дамп исключения или произвольный payload.

Наборы ключей деталей принадлежат тому коду, который их формирует:

- конфигурационные отказы добавляют ключ с путём файла, а отказ о неподдерживаемой схеме — ещё и
  версию схемы из файла ([application-configuration.md](../../reference/application-configuration.md));
- отказы MuMu добавляют только machine-stable факты: режим выбора и identity экземпляра, число
  найденных экземпляров и установок, причину отказа и код ошибки провайдера, требуемое и наблюдаемое
  состояние, фазу операции, код выхода control surface и прошедшее время; пути установки, полный вывод
  control surface и полное observation evidence в details не попадают;
- отказы Android readiness и lifecycle игры добавляют только machine-stable факты: точный endpoint,
  идентификатор пакета, наблюдённое и требуемое состояние игры, фазу операции, код выхода команды ADB,
  прошедшее время, machine-stable причину отказа, identity экземпляра, число совпавших
  launcher-компонентов и bounded evidence наблюдения. Ключ пакета присутствует только у форм, которые
  действительно относятся к пакету: форма отмены операции готовности пакета не содержит, потому что
  готовность наблюдается до всякой работы с пакетом. Абсолютные machine-пути (в том числе путь bundled
  ADB — от него сообщается только имя файла), полный stdout/stderr команд ADB и полный список процессов
  устройства в details не попадают;
- проекция native boundary добавляет тип исходного исключения, имя native библиотеки и код возврата
  native стороны, если он присутствует в замороженном сообщении bridge; для неожиданного исключения
  сообщение формирует сама проекция, поэтому текст исходного исключения наружу не утекает.

`Message` — человекочитаемый текст для оператора на русском языке; он не является machine-readable
контрактом и может меняться без изменения кода отказа.

## Проекция отказов платформенной и native boundary

Проекция выполняется `NativeBoundaryFailureMapper` в `src/AzurPilot.Windows`: это чистая функция без
состояния, которая ничего не логирует, не бросает исключений и не добавляет новых кодов. Она
переводит исключения границы в application-отказ, сохраняя код возврата native стороны как
диагностический факт:

- недоступная native библиотека → `NativeUnavailable`, повтор имеет смысл;
- несовместимый ABI → `NativeIncompatible`, повтор без пересборки бесполезен;
- отмена операции → `OperationCancelled`;
- прочие ошибки границы и неожиданные исключения → `InternalError`.

Application host получает готовую проекцию из DI и не дублирует её логику. Ожидаемый отказ native
boundary не выбрасывается наружу: диагностика возвращает его данными, а решение о продолжении запуска
принимает startup ([runtime-diagnostics.md](../../operations/runtime-diagnostics.md)).

## Отказы MuMu lifecycle

MuMu-коды разделены по владельцу причины. Платформенный adapter `AzurPilot.Windows` сообщает
`MuMuInstallationNotFound`, `MuMuInstallationAmbiguous` и `MuMuControlSurfaceUnsupported`: он видит
файловую систему, control surface и форму её ответа. Adapter сообщает и `MuMuLifecycleTimeout` — когда
отдельная команда control surface не уложилась в свой дедлайн: это отказ одной команды, поэтому он
возникает и у команд, которые ничего не меняют (`version`, перечисление экземпляров, сведения об
экземпляре), и mutation при нём не выполняется. Отсутствие установки и её неоднозначность adapter
различает сам: несколько подтверждённых установок дают `MuMuInstallationAmbiguous`, потому что
`MuMuInstallationNotFound` утверждал бы «MuMu не установлен», а найденная установка без поддерживаемой
точки входа даёт `MuMuControlSurfaceUnsupported`. Первая попавшаяся установка при неоднозначности не
выбирается. `MuMuInstanceNotFound` и `MuMuInstanceAmbiguous` выводит разрешение выбора
в Core по перечисленному набору экземпляров: автоматический выбор разрешается только при ровно одном
экземпляре, явный — только по stable identity, а отображаемое имя identity не является. Core
(`MuMuLifecycleService` в `src/AzurPilot.Core/MuMu/`) не синтезирует отказ, если host вернул
ожидаемый отказ: такое значение пробрасывается без изменений, поэтому диагностика сохраняет исходную
причину, а `InternalError` для ожидаемых MuMu-отказов не используется. Core добавляет только два кода
и только по доказанному условию:

- `MuMuLifecyclePostconditionNotMet` — mutation действительно выполнена и её код выхода сигналит
  отказ, а требуемое состояние экземпляра не наблюдается; достигнут ли к этому моменту deadline
  операции, значения не имеет, потому что причина не во времени;
- `MuMuLifecycleTimeout` — код выхода нулевой, deadline операции достигнут, а требуемое состояние так
  и не доказано; это отдельное условие, а не дедлайн одной команды, который adapter сообщает тем же
  кодом; единственный MuMu-код с `IsRetryable = true`;
- отмена на любой фазе (ожидание координации, mutation, polling) даёт `OperationCancelled` с фазой в
  details, а не MuMu-код.

Код выхода control surface не является доказательством ни успеха, ни отказа: успех операции
подтверждается только наблюдением требуемого состояния конкретного экземпляра, поэтому нулевой код
выхода без наблюдения даёт `MuMuLifecycleTimeout`, а ненулевой код выхода при наблюдённом состоянии
даёт успех. Отображаемое имя экземпляра identity не является и в выборе не участвует.

## Отказы Android readiness и lifecycle игры

Условия этих отказов принадлежат [android-game-lifecycle.md](../../architecture/android-game-lifecycle.md); здесь описан
владелец кода и признак повторяемости.

Платформенный adapter `AzurPilot.Windows` сообщает два кода, потому что видит файловую систему,
executable, control surface и форму ответа ADB:

- `AndroidAdbUnavailable` — bundled ADB обнаруженной установки недоступен: executable не найден, процесс
  не удалось запустить или форма ответа команды версии не распознана. Причина в details machine-stable,
  а от пути executable сообщается только имя файла;
- `AndroidEndpointUnavailable` — точный endpoint выбранного экземпляра не разрешён: сведения установки
  не сообщили пригодного host или порта. Этим же кодом сообщается команда ADB, не завершившаяся в
  пределах своего дедлайна: точный target не ответил, а повторное подключение и завершение сервера ADB
  не выполняются. Ожидаемый отказ чтения сведений не подменяется кодом «установки нет»: adapter сообщает
  именно то, что адрес не разрешён.

Core (`src/AzurPilot.Core/Android/`) синтезирует остальные коды и только по доказанному условию:

- `AndroidTransportNotReady` — transport точного target-а не доказанно готов к командам в пределах
  границы ожидания подключения или общего deadline готовности;
- `AndroidNotReady` — shell недоступен или загрузка Android не завершена в пределах deadline операции;
  единственный Android-код readiness с `IsRetryable = true`, потому что недостижение готовности не
  доказывает её невозможность;
- `AzurLanePackageMissing` — устройство подтвердило отсутствие пакета игры; недоказанное присутствие
  пакета этим кодом не сообщается;
- `AzurLaneStateUnknown` — наблюдение не доказало ни одного состояния игры. Код fail-closed: недоказанное
  состояние не выдаётся ни за «остановлена», ни за «запущена», и mutation при нём не выполняется;
- `AzurLaneLauncherUnresolved` — launcher-компонент не разрешён: компонента нет либо запрос не дал
  распознанного ответа. Оба случая дают один код, но в details попадает именно наблюдённый статус, а не
  жёстко «компонента нет»;
- `AzurLaneLauncherAmbiguous` — подходящих launcher-компонентов несколько, а запуск адресуется одному;
- `AzurLaneLifecyclePostconditionNotMet` — mutation игры действительно выполнена, её код выхода сигналит
  отказ, а требуемое состояние не наблюдается; достигнут ли к этому моменту deadline, значения не имеет,
  потому что причина не во времени;
- `AzurLaneLifecycleTimeout` — код выхода последней выполненной mutation нулевой, deadline операции
  достигнут, а требуемое состояние игры так и не доказано; единственный Android-код lifecycle с
  `IsRetryable = true`;
- отмена на любой фазе (ожидание координации, mutation, bounded polling) даёт `OperationCancelled` с
  именем фазы в details, а не Android-код. Форма отмены операции готовности не несёт ключ пакета, потому
  что готовность наблюдается до всякой работы с пакетом.

Неразрешение launcher-компонента — единственный случай, когда один и тот же код сообщается и
платформенной стороной, и Core: adapter сообщает его, когда запрос mutation приходит к нему напрямую,
Core — когда разрешает launcher до mutation. В details обеих сторон попадает наблюдённый статус
разрешения, поэтому «компонента нет» и «разрешение не доказано» не выдаются друг за друга.

Код выхода команды ADB не является доказательством ни успеха, ни отказа: успех операции подтверждается
только доказанным наблюдением требуемого состояния игры, поэтому нулевой код выхода без наблюдения даёт
`AzurLaneLifecycleTimeout`, а ненулевой код выхода при наблюдённом состоянии даёт успех. Ожидаемые
Android-отказы, возвращённые host-ом, Core пробрасывает без изменений и не подменяет
`InternalError`.

## Коды выхода процесса

Ожидаемый отказ завершает запуск явным предсказуемым ненулевым кодом выхода, поэтому «нездоровый»
запуск нельзя спутать с успешным. Соответствие «application-код отказа → код выхода» задано ровно в
одном месте — `AzurPilotExitCode` в `src/AzurPilot.App/`; значения кодов выхода принадлежат этому
типу и здесь не дублируются. Каждый код из таблицы выше обязан иметь проекцию в `AzurPilotExitCode`;
новый код получает её в том же изменении, а расширение выполняет владелец этого типа. Коды Android
readiness и lifecycle игры спроецированы так же, как остальные: новый код получает следующее свободное
значение и добавляется в конец блока, а значения уже опубликованных кодов не меняются, потому что код
выхода — часть контракта startup.

## Границы модели

- Модель не является каталогом ошибок будущих подсистем и не расширяется «на будущее».
- Модель не содержит retry policy, backoff, circuit breaker или иной автоматики повторов: она
  сообщает признак повторяемости, а решение принимает вызывающая сторона.
- Модель не является presentation-слоем: человекочитаемый итог запуска — поверхность вывода
  application host, а не часть контракта отказа.
