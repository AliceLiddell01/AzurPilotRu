# Игровая геометрия, распознавание и безопасное нажатие

Игровые операции адресуют Azur Lane Global/EN на точно выбранном экземпляре MuMu. Через
[Agent CLI](../reference/agent-cli.md) доступны наблюдение известных ассетов, проверка
соответствия координат ввода, Dock roundtrip и самостоятельное обеспечение главного UI из выключенного окружения.

## Готовность главного UI

`game-ui-ready-observe` ничего не запускает, не подключает и не нажимает. Операция возвращает
классификацию экрана; `Ready` требует нескольких независимых положительных признаков главного меню,
стабильных кнопок Dock/Depot/Battle, доказанных отрицательных guards перекрытий,
свежего foreground Global/EN и полноэкранного viewport. Фон и персонаж не сравниваются с эталоном.
Подтверждение накапливается только на независимых новых кадрах с устойчивым размером.
Один баннер `Login successful!`, foreground или успешный ADB не доказывает готовность.

`game-ui-ready-ensure` под одной общей lease использует существующий MuMu/Android/game lifecycle,
затем `GameUiReadinessService`. Уже запущенное окружение переиспользуется. Правила состояний и
разрешённых переходов находятся в `catalog.json/readiness`, а ограничения бездействия и действий —
в Core. Возврат из обычного Dock, LOG IN существующей сессии и старт со стадии SERVER выполняются через
`GameUiActionRunner`. Для конкретного окна загрузки игровых файлов обязательны одновременно
Update, текст `This update requires downloading` и Confirm. Подтверждение кнопки не является
универсальным разрешением на обновление клиента: иное содержание окна остаётся неизвестным.

Postcondition действия может быть началом известной загрузки либо новым игровым состоянием;
исчезновение кнопки само по себе недостаточно. Начало загрузки не завершает ensure: далее следуют
пассивное ожидание и отдельное устойчивое подтверждение Ready. Баннер успешного входа только
ожидается. Каждый переход каталога выполняется не более одного раза за flow; Unknown, отсутствие эффекта,
неизвестный guard, смена endpoint и отмена не порождают слепой tap/restart/rollback.
После доказанного старта из `Stopped` начальный нераспознанный экран пассивно ожидается отдельно
ограниченное время, пока впервые не появится поддерживаемое состояние (`initial_transition_unproven`
при превышении). Он остаётся `Unknown`, без выдуманного Loading и без ввода, и не увеличивает ожидание
неизвестного экрана после уже распознанного состояния. Для работающей игры такое ожидание не включается.

### Старт со стадии SERVER

Надпись `PRESS TO START` пульсирует, полупрозрачна и видна уже на экране LOG IN, поэтому не является
признаком состояния. Как `LOGIN_CHECK` оригинала, переход использует непрозрачную плашку CRIWARE
(`login.criware`) только как якорь и отдельную логическую `tapArea` действия `login.start`. CRIWARE
присутствует и на LOG IN, поэтому ввод разрешает лишь совокупность: стадия SERVER (`login.server`,
логотип), доказанное отсутствие LOG IN, баннера, Update и overlay guards, свежий кадр, viewport и
однократный `GameTap`. Область ввода совпадает с `LOGIN_CHECK.button` оригинала, проверена на текущих
4K-кадрах: она лежит на фоне справа от панели сервера и не пересекает ROI якоря и обязательных признаков;
каталог отвергает пересечение при загрузке, runner — пересечение с найденным якорем.

### Сроки и прогресс загрузки

Общий срок операции принадлежит вызывающему: для Agent CLI это `--timeout-ms`, при истечении которого
возвращается `AgentDeadlineExceeded` с сохранёнными фазами и возможным эффектом. Operator и Core не
вводят более короткого скрытого срока. Собственные пределы Core имеют явные причины: бездействие
известного/неизвестного экрана, отсутствие роста прогресса загрузки, начальный неизвестный экран и
верхняя граница вызова без внешнего deadline, не меньшая максимального агентского срока.
Read-only наблюдение ограничено числом кадров, а не временем.

Загрузка бывает двух видов с разной семантикой ожидания.

- **Стартовая загрузка без обновления** (`loading.startup`: подписи `Checking for updates...` и
  `Update complete. Loading game...`) — пассивное ожидание без ввода. Полоса на этом экране уже
  заполнена, кубик в углу может вращаться или подвисать, иллюстрация меняется: ничто из этого не
  прогресс. Срок отсчитывается от первого входа в загрузку и не продлевается; повторный вход после
  кратковременного нераспознанного кадра его не перезапускает (`loading_unfinished`). Распознанная
  загрузка остаётся частью стартового перехода: ожидание неизвестного экрана после неё не сокращается.
- **Скачивание игровых файлов** (`loading.download`) получает право продлевать ожидание только после
  подтверждённого в этом же flow действия `update.download` (Confirm), кадр-доказательство которого
  показал измеримую полосу. Её начальная доля — точка отсчёта. Ожидание продлевает лишь новый максимум
  доли заполнения; снижение, сброс к нулю, колебания и возврат к прежнему значению его не продлевают
  (`loading_no_progress`), а пассивный срок рост только продлевает, не сокращая. Любой кадр вне загрузки,
  включая неизвестный, снимает это право до конца flow; новая операция начинает без него. Скачивание
  без подтверждённого Confirm ожидается как пассивная загрузка.

Каталог задаёт для владельца полосы `progress`: логическую область, число равных сегментов и цветовые
пороги заполненной и пустой частей. Host измеряет каждый сегмент существующей native RGB-статистикой без
выдачи пикселей. Доля — число заполненных сегментов слева; допустима только картина «заполненные — не
более одного граничного — пустые», иначе доля неизвестна (`null`) и прогрессом не считается. Яркость фона,
трека и подписи не меняет долю. Подпись скачивания центрирована, и её начало сдвигается при изменении
длины чисел, поэтому область поиска `loading.download` шире шаблона только по горизонтали. Рост не
доказывает успешность загрузки, его отсутствие — зависание сети. Медленная многосотмегабайтная загрузка
может закончиться deadline вызывающего: это явный незавершённый итог, а не Ready и не повод для повторного ввода.

### Фазовая телеметрия

Итог ensure содержит фазы `lifecycle:*` (lease, MuMu, Android, процесс игры) и UI-фазы
`state:<правило>`, `state:unknown`, `action:<переход>` на одной монотонной шкале от начала операции.
Каждая фаза имеет момент входа/выхода, суммарное время посещений, причину завершения и собственную
работу бота: захваты (ADB-команда, декодирование), распознавание, проверки viewport, ввод и пассивные
паузы. Невстреченная фаза — `NotObserved` без длительности. Время фазы — это время, пока бот видел
состояние, с разрешением в один захват; работа бота — его часть. Пиксели, сервер и аккаунт не выводятся.

Каждый итог действия содержит `timing`: длительность, момент возврата команды ввода, начала захвата
последнего кадра без эффекта и кадра-доказательства (смена экрана игрой лежит между ними с точностью до
одного захвата) и собственную работу бота внутри действия. Dock roundtrip дополнительно сообщает моменты
получения аренды, конца подготовки transport и итога сценария внутри процесса.

Уже классифицированный кадр используется действием как исходный: все guards, свежесть и viewport
проверяются на нём перед вводом, а дублирующий захват не выполняется. В Dock roundtrip исходным кадром
возврата служит кадр-доказательство открытия; поэтому `dock.open` проверяет то же надмножество guards, что
и `dock.close`. Viewport доказывается для каждого
кандидата Ready, итогового кадра read-only наблюдения, перед вводом и в postcondition; пассивные кадры
ожидания им не подтверждаются и не служат доказательством. Пауза между захватами — только остаток
минимального интервала после начала предыдущего захвата.
### Граница профиля и неизвестные окна

Как в историческом `is_in_main`, идентичность главной страницы определяется элементами UI.
Дополнительно проверяются несколько независимых кнопок и устойчивость кадров. Модальный крест
закрытия ищется в ограниченной ROI независимо от заголовка/назначения диалога; открытая левая
панель распознаётся по заголовку Commissions без значений наград. Эти guards не имеют safe tap
и не разрешают закрывать окно. Неизвестное содержание окна с поддержанным оформлением возвращает
`RequiresUserAction`, даже если Update/Confirm не распознаны и все main-кнопки видимы.
Guards повторно проверяются перед действиями и в postcondition; Unknown/неоднозначность блокируют ввод.

Поддержка ограничена UI-темой кнопок и оформлением перекрытий из каталога. Произвольное окно
другого оформления без распознаваемых признаков не покрывается этим детектором; отсутствие
известного шаблона не является универсальным доказательством отсутствия любых окон.
Отдельных согласованных оригиналов безопасных объявлений пока нет: награды, соглашения,
клиентское обновление, секреты и неизвестные ошибки не получают автоматического разрешения ввода.

## Владельцы

- [Core/Game](../../src/AzurPilot.Core/Game/) содержит типы координат, сведения о происхождении кадра, однократное
  разрешение `GameTap` и общий `GameUiActionRunner`.
- [Windows/Game](../../src/AzurPilot.Windows/Game/) связывает существующий адаптер захвата снимков с
  нативным распознаванием. `NativeFrame` остаётся единственным владельцем полного RGB8-кадра.
- [Каталог](../../assets/game/catalog.json) владеет смысловыми ID, происхождением crops, вариантами,
  режимами сопоставления, ROI, порогами, безопасными областями и сроками действий.
- [C ABI](../../native/include/azurpilot_native_abi.h) владеет формой результата сопоставления и бюджетами.
- `AzurPilotOperatorService` разрешает точный endpoint и держит существующую межпроцессную аренду
  на протяжении полного сценария. Вложенные шаги аренду повторно не захватывают.

## Координаты и native поиск

`GameGeometry` отделён от диагностических `ScreenshotDiagnosticRegions`. Логическая система координат
описывает UI; физическое разрешение приходит из метаданных нативного кадра. Поддерживается точное
соотношение 16:9 в альбомной ориентации от 720p до 4K. Границы ROI округляются наружу, безопасной области — внутрь.
Обрезания области по границам кадра, автоматического вращения и догадок о letterboxing нет. Поддержка 8K не заявлена:
нынешние бюджеты декодера и проверенный диапазон геометрии для неё недостаточны.

OpenCV читает ROI через заголовок `cv::Mat` без копирования полного кадра. Масштабируется маленький
шаблон, а не снимок. Каталог кеширует только закодированные crops; временные нативные шаблоны и карта оценок
освобождаются в одном синхронном вызове. Декодер проверяет отдельный бюджет шаблона до выделения RGB.
Текущие плоские кнопки используют яркость, заголовок Dock — RGB. Для этих непрозрачных crops маска
не нужна. Добавление нового ассета требует проверки его собственных положительных и отрицательных
образцов; совместимость произвольных UI-версий не предполагается.

### Выбор игровых ассетов

1. Сначала изучается решение `AzurPilot-private-Ru@personal/stable` для того же экрана: `Button.area`,
   `Button.button`, режим, ROI, альтернативы и назначение. Оригинал — проверенный ориентир, а не
   эталон: отклонение обосновывается независимыми кадрами и замерами, координаты переносятся только
   после проверки версии UI, системы координат и безопасной области ввода.
2. Признак выбирается статичным, непрозрачным и не зависящим от фона. Мигающие, пульсирующие,
   движущиеся и циклические элементы не используются, если есть пригодная статическая альтернатива;
   смысл и надёжность признака важнее формы crop.
3. Crop исключает иллюстрации, персонажей, анимацию, числа, полупрозрачные подложки и эффекты: узкая
   информативная область или несколько независимых якорей. Прозрачный PNG не означает игнорирования
   фона: текущий RGB8 TM_CCOEFF_NORMED/MAE не поддерживает маску, и маскированный поиск требует
   отдельной реализации и доказательства корректности метрик.
4. Неизбежная анимация без статического якоря (как анимированные сирены оригинала) допускает маленький
   многокадровый GIF с характерными фазами или эквивалентное представление фаз. Это отдельная capability
   native/ABI с проверкой всех фаз, стоимости декодирования/сопоставления, координатного поиска и
   ложных срабатываний; ради принципа при наличии статического признака она не добавляется.
5. Положительный вывод требует независимых реальных источников (другая фаза, фон или версия UI) и
   негативных экранов, а не только кадра, из которого вырезан crop. Пороги и ROI обосновываются
   наблюдениями; граница поддерживаемых вариантов остаётся явной. Недостаток независимых оригиналов
   фиксируется как непроверенное, без ослабления порогов.
6. Подпись на полупрозрачной подложке неизбежно содержит фон между глифами. Для пассивного признака без
   ввода (`loading.startup`) crop ограничен высотой глифов, сравнивается по яркости, а пороги выбраны между
   независимыми позитивами и негативами той же области экрана; для признака, разрешающего ввод, такое
   основание недостаточно.

`Unique` требует достаточной корреляции, допустимой ошибки пикселей и отрыва от второго независимого кандидата.
`Absent`, `Ambiguous`, `GeometryRejected` и `TechnicalFailure` сохраняются отдельно. Оценка не является
вероятностью. Второй максимум ищется вне окрестности первого размером в половину шаблона по каждой
оси; соседние положения одного и того же элемента не считаются разными кнопками.
Официальная семантика метода: [OpenCV matchTemplate](https://docs.opencv.org/4.x/df/dfb/group__imgproc__object.html).

## Ввод и доказательство эффекта

Перед нажатием свежий исходный признак должен быть `Unique`, а независимый признак результата — `Absent`.
Все исключающие признаки перехода должны быть доказанно `Absent` до ввода и после него. В текущем
переходе кнопка подтверждения выбора кораблей исключает режим выбора: общий заголовок Dock сам по
себе не доказывает обычный Dock. Эта кнопка не имеет безопасной области ввода и никогда не нажимается. Проверяются
устройство, физические размеры, внутренняя безопасная область, возраст кадра по монотонным часам от начала захвата,
передний план Global/EN и полноэкранное окно Android. `dumpsys input` должен доказать одинаковые
логические/физические границы и размеры устройства для display 0; rotation согласуется с конфигурацией окна.
Неизвестный формат, конфликтующие области отображения, inset/app bounds, перекрытое окно или compat scaling
отклоняются. Shell input получает координаты текущего логического дисплея; поворот сенсорного устройства
повторно не применяется. Основание —
[AOSP InputShellCommand](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/core/java/com/android/server/input/InputShellCommand.java).

Только Core создаёт `GameTap`; адаптер Windows повторно проверяет срок и атомарно расходует разрешение.
Одно нажатие адресуется тем же поставляемым ADB и точным endpoint, с явным display 0. Произвольных XY через CLI нет.
Произвольный swipe пока не публикуется: у текущего проверенного сценария нет такого действия.

После нажатия новый захват должен начаться после завершения команды, принадлежать тому же устройству и
разрешению и независимо подтвердить новый признак с исчезновением исходного. Проверка ограничена
дедлайном и не повторяет нажатие. `Unknown`, отказ ADB и отмена сохраняют возможный частичный эффект.
Успех ADB не подтверждает переход. При отмене или отказе автоматический возврат не выполняется;
успешное открытие и подтверждённое возвращение отражаются отдельно.

Аренда координирует AzurPilot, но не посторонние инструменты ADB и действия пользователя. Проверка области игры
уменьшает окно гонки; аппаратной атомарности между наблюдением и вводом Android не предоставляет.

## Сопоставление с оригиналом

Предметный ориентир — `AzurPilot-private-Ru`, ветка `personal/stable`, а не её `main`.

| Механизм оригинала | Решение текущей реализации |
| --- | --- |
| `module/device/screenshot.py`: ориентация, интервал снимков, время жизни изображения | Сохранены проверка размеров/ориентации и свежесть. Захват остаётся в существующем адаптере Windows с нативным кадром; глобального уменьшения до 720p нет. |
| `module/base/button.py`: отдельные `area`/`button`, смещение ROI, luma и проверка цвета | ROI поиска и безопасная область ввода принадлежат данным; найденное смещение переносит безопасную область. Отдельная `tapArea` действия соответствует раздельным `area`/`button`, но требует контекста стадии и непересечения с видимыми признаками. Для разных crops выбраны luma/RGB и независимая проверка ошибки пикселей. |
| `module/base/template.py`, `utils.py`: масштабирование шаблона и варианты | Масштабируется только шаблон; варианты хранятся в каталоге. Общего снижения порога на другом разрешении нет. |
| `module/base/resource.py`: кеширование и освобождение ресурсов | Небольшой ограниченный кеш закодированных шаблонов и RAII временных нативных объектов; полного RGB-кадра в managed памяти нет. |
| `module/device/control.py`, `method/adb.py`: кнопка → координата → ввод Android | Безопасный центр однократного разрешения идёт через существующий поставляемый ADB и точный endpoint; случайные координаты и старый стек устройства не переносятся. |
| `module/ui/ui.py::ui_click`: appear → click → check | Одно нажатие и отдельные последующие наблюдения под общим дедлайном. Цикл повторных кликов/автоматического восстановления не переносится. |
| `module/handler/login.py::_handle_app_login`, `handle_app_login`, `app_start` | Свежие последовательные кадры, известные login-состояния, ограниченное ожидание, устойчивое подтверждение главного экрана. Generic popup confirm, сбор наград и restart/очистка данных не перенесены. |
| `module/ui/ui.py::is_in_main`, `ui_page_main_popups`, `ui_goto_main`; `page.py`, `ui_white/assets.py` | Главный экран и обычный Dock различаются по подтверждённым Global/EN white UI-ассетам. Остальная legacy-карта страниц и варианты UI не импортируются. |
| `module/handler/assets.py`: LOGIN/UPDATE/ANNOUNCE/RETURN | `LOGIN_CHECK` (CRIWARE + отдельный `button`) перенесён как якорь и `tapArea`, дополнительно ограниченные стадией SERVER. Назначение остальных окон проверяется по пользовательским оригиналам. Автоматический Confirm разрешён только конкретной загрузке игровых файлов. Для остальных окон нужны отдельные исходники и правила. |
| `module/application/legacy_game_adapters.py::LegacyGameApplicationAdapter.login_to_main` | После переходов заново проверяются UI и foreground/viewport; сообщение об успешном входе не заменяет postcondition. |
