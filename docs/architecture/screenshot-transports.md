# Транспорты снимков экрана, выбор `auto` и измерения

## Граница

Единственный production-владелец захвата — `ScreenshotCaptureRouter` (`src/AzurPilot.Windows/Capture/`). Он
реализует существующий `IAndroidScreenshotHost`, поэтому game UI, readiness, Dock, `screenshot-scan`, TUI и
Debug Mode получают кадры прежним путём и не знают о транспорте. Второго владельца захвата, оркестратора или
каталога координат нет: транспорт меняет только способ получения RGB8-кадра `NativeFrame`.

Каждый транспорт отдаёт кадр, проверенный по ширине, высоте, шагу строки и формату RGB8, с provenance exact
MuMu identity и endpoint, моментом начала захвата и разложением времени `Acquisition`/`Decode`/`EndToEnd`
(`ScreenshotCaptureTiming`). Факты, присущие только ADB PNG (длительность команды, байты PNG, exit code), лежат
отдельно в `AdbPngCaptureFacts`; у потоковых транспортов есть `ScreenshotStreamFrame` с номером кадра.

Различаются: успешный вызов, получение нового кадра, новая последовательность видеопотока, визуальное
изменение пикселей и доказанное постусловие. Для запрос-ответных транспортов каждый успешный захват — новый
кадр; для scrcpy новым считается только кадр с номером больше выданного ранее и пришедший после запроса с
учётом консервативной границы конвейера. Повтор кадра потока свежим не считается.

## Девять транспортов

Машинная матрица — `CaptureCompatibility` (команда `agent capture-methods`). Кратко:

| Транспорт | Доставка | Формат до RGB8 | Условия и ограничения |
| --- | --- | --- | --- |
| `ADB` | запрос | PNG `screencap -p` через `exec-out` | эталон корректности и bootstrap `auto` |
| `ADB_nc` | запрос | raw `screencap` через `nc` и `adb reverse` | нужен `nc`/`busybox nc`; слушатель только `127.0.0.1`, одно соединение от loopback |
| `uiautomator2` | запрос | JPEG из JSON-RPC закреплённого `u2.jar` | JPEG с потерями |
| `aScreenCap`, `aScreenCap_nc` | запрос | BMZ1 (LZ4 BMP) | сборки только для SDK 21–28; на новом Android capability probe фиксирует отказ компоновщика как UNSUPPORTED |
| `DroidCast` | запрос | PNG `/preview` | физический буфер дисплея, поворот выполняет DLL |
| `DroidCast_raw` | запрос | RGB565 `/screenshot` | то же; 5–6 бит на канал |
| `scrcpy` | поток | H.264 → Media Foundation | без `downsize_on_error`: кодер, не принявший разрешение, даёт UNSUPPORTED |
| `nemu_ipc` | вызов DLL | RGBA с вертикальным отражением | только MuMu; DLL берётся из обнаруженной установки |

`ldopengl` не поддерживается: проект не зависит от LDPlayer.

### Native boundary

ABI v6 (`native/include/azurpilot_native_abi.h`) добавляет к PNG-пути создание кадра из сырых форматов
(RGBA/BGRA/RGB/BGR/RGB565, stride, вертикальное отражение), декодирование BMZ1 и JPEG, поворот кадра на
четверть оборота, сессию `nemu_ipc` и H.264-декодер Media Foundation с выдачей последнего кадра после
заданного номера. Пиксели не проходят через PNG round-trip, полный 4K RGB не копируется в C#, указатели не
выходят за `SafeHandle`.

`nemu_ipc` загружает `external_renderer_ipc.dll` только по полному пути внутри обнаруженной установки MuMu
(`LoadLibraryExW` с поиском зависимостей в каталоге DLL и System32), проверяет путь, отсутствие reparse point,
разрядность PE и экспорты. Экземпляр выбирается по индексу exact identity, а не по порту. Вызовы DLL идут на
выделенном потоке с тайм-аутом: зависший вызов помечает сессию сломанной и не блокирует команду бесконечно.
DLL MuMu пишет диагностику в CRT stdout; Agent CLI до загрузки native-компонентов перенаправляет fd 1 и
`STD_OUTPUT_HANDLE` в NUL и пишет envelope в сохранённый дубликат исходного stdout.

### Helper-ы на устройстве

Зависимости (`scrcpy-server`, `u2.jar`, `DroidCast_raw`, сборки aScreenCap) закреплены в
`native/capture-dependencies.json` с URL, версией, лицензией и SHA-256. CMake скачивает их при configure и
сверяет hash; сборка кладёт их в `capture/` рядом с приложением; runtime повторно сверяет SHA-256 и не
скачивает ничего во время работы. На устройство файл отправляется в `/data/local/tmp/azurpilot-capture` и
проверяется `sha256sum`.

Helper запускается `CLASSPATH=<jar> nohup app_process …` на случайном порту устройства; хост ходит к нему через
target-scoped `adb -s <endpoint> forward tcp:0`. Остановка — `kill` только PID, чей `/proc/<pid>/cmdline`
содержит маркер класса helper-а; `pkill -f` и остановка чужих процессов не используются. Глобальное состояние
ADB-сервера не меняется. Shell-аргументы проходят через белый список символов.

Каждый ресурс (helper, forward, reverse) записывается в журнал
`%LOCALAPPDATA%\AzurPilot\capture-helpers\<endpoint>.json` до использования и удаляется после освобождения.
Ресурсы процесса, который завершился (например, worker, остановленный по сроку), освобождаются при
следующем открытии транспорта на том же endpoint или явно родительским измерением.

## Выбор транспорта

Настройка `screenshot.method` — `auto` или одно из девяти имён
([конфигурация](../reference/application-configuration.md)). Явный метод не подменяется: его отказ, включая
UNSUPPORTED, возвращается вызывающему с `reason`, `method`, `verdict`.

`auto` использует ADB, пока для отпечатка target нет калибровки. Отпечаток — SHA-256 от identity, версии MuMu,
версии и SDK Android, ABI устройства, SHA-256 manifest зависимостей и версии native ABI. Калибровку
(`%LOCALAPPDATA%\AzurPilot\capture-calibration.json`) записывает только `capture-benchmark` после доказанного
главного экрана до и после измерения. Изменение любого компонента отпечатка делает калибровку неприменимой,
изменение разрешения обнаруживается по кадру и инвалидирует её. Отказ калиброванного метода в `auto` —
наблюдаемый откат на ADB (`ScreenshotSelection.FallbackFrom`, причина `method_failed:<reason>`); в этом процессе
метод повторно не пробуется. Выбор и его причина видны наблюдателю и в Debug-отчёте (`methods`, `method` кадров).

## Измерение транспортов

`agent capture-benchmark`:

1. Проверяет главный экран `game-ui-ready-observe`-путём; без `Ready` — `BLOCKED`, ввода в игру нет.
2. Для каждого метода запускает отдельный процесс `agent capture-probe` с бюджетом
   `оставшееся время / оставшиеся методы`. Worker ограничен временем жизни процесса; после остановки по сроку
   родитель освобождает его ресурсы устройства по журналу.
3. Worker: эталонный кадр ADB → подготовка транспорта (setup отдельно) → прогрев → серия подряд → эталон ADB →
   освобождение. Корректность доказывают два сравнения с эталоном по сетке 16×9 средних RGB с допуском и
   проверкой порядка каналов (перестановка R/B должна давать заметно большую ошибку).
4. Повторно проверяет главный экран; без него калибровка не записывается.
5. Выбирает метод (`ScreenshotMethodSelection`): к выбору допускаются `PASS` и `PARTIAL` (серия, урезанная только
   сроком) без отказов, с доказанной корректностью и не менее 5 успешными кадрами; порядок — p95 end-to-end
   (равенство в пределах max(1 мс, 5%)), затем частота новых кадров, медиана. Разные разрешения не
   сравниваются. Без допустимого кандидата — `NO_VALID_CANDIDATE` (`FAILED`).
6. Пишет `report.json` и `summary.md` в `.codex/local/reports/capture-benchmark/<run-id>/`.

Статусы: `PASS`, `FAILED`, `UNSUPPORTED`, `BLOCKED`, `PARTIAL`, `NOT_TESTED`, `INSUFFICIENT`, `UNVERIFIED_SCENE`.
`UNSUPPORTED` — наблюдённая неприменимость на этом target (нет `nc`, компоновщик отверг бинарник, кодер не
принял разрешение), а не общий отказ транспорта. Профили `short`/`full`/`stress` задают 25/200/1000 снимков;
общий срок команды по-прежнему не больше 300 000 мс, поэтому медленные методы при полном наборе получают
`PARTIAL`/`INSUFFICIENT`, а полный профиль запускается подмножеством `--methods`.

CPU worker-а измеряется для его процесса (без эмулятора и ADB), рядом — загрузка системы. `--debug-overhead true`
повторяет серию победителя с Debug Mode и сообщает разницу p50/p95 и CPU.

## Интервалы

`agent capture-intervals` измеряет выбранный транспорт по расписанию start→start: следующий захват не раньше
`start + период`, опоздание не догоняется пачкой. Точка сетки — прогрев 2 захвата и не меньше
max(2 с, 4,5 × интервал), чтобы любой интервал мог набрать минимум 5 кадров. Классы: `Stable` (≥90% целевого FPS,
≤10% пропусков, p95 start→start ≤ интервал + max(2 мс, 10%)), `Unstable`, `Unachievable` (медиана вызова больше
интервала с допуском), `Failed`.

Фаза `normal` требует доказанный главный экран до и после и завершается статусом
`AWAITING_USER_COMBAT_CONFIRMATION` с одноразовым кодом и сроком 30 минут; процесс при этом не ждёт человека.
Фаза `combat` — отдельный вызов той же сессии с кодом, после того как пользователь сам открыл бой и явно
подтвердил это. Код проверяется вместе с target, методом и сроком; повторное использование отклоняется. Если
главный экран распознан, бой не начат — отказ `scene_is_main`. Распознавателя боя нет, поэтому итог боя —
`UNVERIFIED_SCENE` со сценой `USER_CONFIRMED`; возврат на главный экран после измерения — `PARTIAL`. Агент не
нажимает Battle, не переключает экраны и не считает собственное сообщение подтверждением.

Профили `fast`/`balanced`/`low_load`/`current` повторяют формулы исходного benchmark; без измеренного боя их
боевые значения `null`. Задержка последующего распознавания не измеряется (`not_measured`).

Фаза normal записывает в `state.json` сессии привязку (`formatVersion` 2): отпечаток target, версии MuMu и
Android, разрешение кадров, причину выбора транспорта и прогон калибровки, путь и SHA-256 конфигурации и
действующую секцию `screenshot`. Combat-фаза при другом отпечатке отклоняется (`environment_changed`), при
другом разрешении — `PARTIAL` (`resolution_changed`).

## Применение профиля

`agent capture-profile-apply --session <id> --profile <имя>` — единственный путь из измерения в конфигурацию;
после бенчмарка ничего не применяется автоматически.

1. **Preview** (без `--confirm`): команда наблюдает условия тем же production-путём, что observe/Dock (отпечаток,
   один кадр через маршрутизатор с его выбором и откатом, калибровка, свежее чтение конфигурации), проверяет
   привязку сессии и строит план. Конфигурация не меняется. Результат — текущие и новые значения, список
   изменяемых ключей и одноразовый код со сроком 10 минут; новый preview отменяет прежний код.
2. **Apply** (`--confirm <код>`): под исключительной блокировкой `apply.json` код гасится при любой предъявленной
   попытке. Запись разрешена, только если совпали код, профиль, путь и SHA-256 файла из preview, условия
   по-прежнему проходят проверку и план не изменился. Иначе нужен новый preview.

Отказ привязки: `session_binding_missing` (сессия без привязки, записанная до её появления), `session_expired`
(старше 24 ч), `target_mismatch`, `emulator_version_changed`, `environment_changed`, `resolution_changed`,
`method_changed` (другой транспорт либо откат `auto`), `calibration_changed`, `configuration_path_mismatch`,
`configuration_legacy_json`, `configuration_changed` (другая действующая секция `screenshot`). Правка
посторонних ключей файла сессию не инвалидирует, но инвалидирует выданный preview.

Достоверность: `fast`/`balanced`/`low_load` пересчитываются из точек отчётов фаз, а не из `profiles.json`, и
каждая выбранная точка повторно проверяется по порогу устойчивости; несоответствие — `session_results_invalid`.
Нужна фаза normal с `PASS` (иначе `normal_phase_incomplete`). Боевой интервал меняется только при combat
`UNVERIFIED_SCENE`; неизмеренный (`not_measured`) или незавершённый (`phase_incomplete`) бой оставляет
`combatIntervalMs` без изменений. Дробный интервал округляется вверх до целых миллисекунд (33,3 → 34).
`current` — восстановление значений, действовавших при измерении, а не рекомендация.

Запись выполняет `AzurPilotConfigurationStore.SaveScreenshotIntervals`: позиции ключей берутся из событий
YamlDotNet, меняются только значения интервалов либо добавляются недостающие строки (с отступом и переводом
строки документа), комментарии, порядок и BOM сохраняются. Кандидат проверяется строгим загрузчиком,
заменяет файл атомарно с backup и обнаружением конкурентной записи. После записи файл перечитывается и
сверяется с планом: изменены только интервалы, остальные настройки равны прежним.

## Интервалы в продукте

`screenshot.normalIntervalMs` задаёт период наблюдения постусловия игровых переходов (Dock, переходы
readiness). Это нижняя граница периода, а не гарантия: если одно наблюдение (захват и сопоставление шаблонов)
дольше интервала, ожидания нет и интервал на скорость не влияет. `screenshot.combatIntervalMs` — граница
боевого режима: боевой автоматики в продукте пока нет, поэтому значение используется только как `current`
профиля измерения и не влияет на другие команды.
