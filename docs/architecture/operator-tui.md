# Операторский TUI

Операторский TUI — пользовательская поверхность AzurPilot. В нём доступны только уже реализованные
backend capabilities: пустых разделов для будущих игровых задач, расписаний и bot backend нет.

## Границы

`AzurPilot.App` содержит composition root, application-level operator use cases и Terminal.Gui UI.
`OperatorUi` отвечает за renderer, клавиатурную навигацию, режимы доступа и ограниченное состояние
представления. `OperatorServices` связывает выбранную пользователем capability с уже существующими
сервисами MuMu, Android, Azur Lane и screenshot diagnostics. UI не формирует команды ADB, не выбирает
endpoint и не дублирует lifecycle postconditions.

Интерактивный запуск использует тот же application host и один DI container, что и одноразовая
диагностика. Startup snapshot показывается в первой сессии без второго сбора диагностики; host
остаётся запущен до выхода из TUI. Запуск приложения ничего не подготавливает и не мутирует: ни ADB, ни
MuMu, ни игру. При неготовой или отсутствующей MuMu оболочка остаётся доступна и показывает
неизвестное/недоступное состояние.

Если stdin или stdout перенаправлены, Terminal.Gui не запускается: приложение выполняет прежний
одноразовый диагностический путь. Человекочитаемый итог остаётся в stdout, structured JSON logs — в
stderr, окно отдельной лог-консоли не открывается.

## Режимы интерфейса

Режим задаёт объём доступных действий и является настоящим presentation-правилом, а не оформлением.

| Режим | Назначение | Состав |
| --- | --- | --- |
| `normal` | Основной пользовательский режим (default) | Пользовательские операции: запуск и остановка окружения, запуск и остановка игры, состояние, настройки, помощь, выход |
| `manual` | Ручное управление для разработки и troubleshooting | Пользовательские операции плюс категории `MuMu`, `Android`, `Игра` |
| `diagnostic` | Полный технический инструментарий | Всё из `manual` плюс категория `Диагностика`: `/diagnostics`, `/screenshot`, `/details` |

Режим берётся из аргумента `--mode normal|manual|diagnostic` либо из `ui.mode` конфигурации; явный
аргумент запуска имеет приоритет. Неверное значение — отказ запуска, а не молчаливая подстановка
обычного режима.

Технические команды не просто скрыты в обычном режиме: прямой ввод `/instances`, `/android-prepare`,
`/screenshot` и подобных не исполняет внутреннюю операцию. Оператор получает короткое сообщение о
том, что действие доступно в ручном или диагностическом режиме, и точный путь перехода. Единый
каталог действий остаётся единственным владельцем dispatch-имён, а каждый пункт несёт режим
доступности, категорию и human-readable название.

## Действия

Первый уровень палитры короткий: он несёт пользовательские операции режима. Технические команды
доступны только после выбора категории, поэтому технический список не раскрывается первым же `/` или
`F2`. Вложенный уровень возвращается на предыдущий по `Esc`, а не выбрасывает оператора из меню.

`/environment-start` — единственное верхнеуровневое действие подготовки окружения. Оно разрешает
точную identity целевого экземпляра по правилам `mumu.instance`, предъявляет её в едином
подтверждении и только затем запускает MuMu из доказанного `Stopped`, пропускает lifecycle при
`Running` и подготавливает Android до transport/shell/boot readiness. Azur Lane этим действием не
запускается. Ручные `/instances`, `/select` и `/android-prepare` для этого не требуются.

Неоднозначный или недоказанный target не приводит к mutation: при нескольких обнаруженных
экземплярах и значении `auto` оператор получает выбор точного ID в рамках того же действия, а старт
остаётся запрещённым до однозначного выбора. Ошибка preflight прекращает выполнение до следующего
этапа; после уже выполненного старта MuMu может остаться запущенным при отказе или отмене.

`/environment-stop` — безопасная остановка конкретного MuMu с объяснённым подтверждением и
фактическим postflight. `/game-start` и `/game-stop` используют существующий lifecycle Azur Lane
Global/EN.

Запуск игры использует подготовку окружения как зависимость того же запроса, с одним подтверждением:
из `Stopped` запускается точный MuMu, доказывается Android readiness и только затем вызывается game
lifecycle. Сигналы этапов исходят из production orchestration: запуск MuMu, подготовка transport,
проверка shell/boot, запуск игры. UI не вычисляет процент готовности по времени.

`/status` показывает краткое read-only состояние среды. Нормальное состояние `MuMu = Stopped` — не
предупреждение об отказе: экран сообщает, что MuMu остановлен и окружение можно запустить. Технические
failure-коды, correlation identifier и недоступный до запуска ADB endpoint относятся к
диагностическим подробностям и на пользовательском экране не появляются.

`/diagnostics` повторно собирает существующий диагностический snapshot и доступно в диагностическом
режиме. `/android` и `/game` наблюдают состояние только для выбранного instance; наблюдение не
подготавливает transport и не запускает эмулятор или игру. `Unknown` и недоказанные факты отображаются
как неизвестные, а не как подтверждённое отсутствие или готовность.

`/settings` показывает действующую эффективную конфигурацию: источник, версии схемы, минимальный
уровень журнала, режим интерфейса и значение `mumu.instance`. Меню позволяет сохранить точный ID,
создать YAML/мигрировать JSON с backup, выбрать режим и включить отдельную лог-консоль следующего
запуска. Сохранённые значения и путь фактического backup показываются отдельно от текущего snapshot.
Параметры режима и viewer применяются после перезапуска; CLI override не попадает в сохранение.

`/screenshot` выполняет один production capture для выбранной пары instance/endpoint, затем вызывает
production scanner для `FullFrame` и `Center`. UI показывает размеры, pixel bounds и полученные
агрегаты RGB. Эти статистики не определяют, какой экран игры отображён.

Mutation MuMu, Android transport preparation и lifecycle Azur Lane требуют отдельного подтверждения.
По умолчанию подтверждение отменено; для согласия оператор должен явно выбрать его. Выполнение
проходит через существующие orchestration services, mutation gates и проверку результата. Двойной
ввод не запускает вторую операцию, пока занята текущая.

Отмена прекращает текущую операцию по её cancellation contract. Она не откатывает уже выполненную
mutation и не останавливает MuMu/игру автоматически. `/exit` завершает сессию после отмены и
завершения активной операции.

После частичного отказа/отмены подготовки выполняется новое read-only наблюдение exact MuMu.
Неизвестный результат не выдаётся за остановку. Последующее `/status` может показать уже изменившееся
состояние, поэтому отмена сама по себе не является postcondition ресурса.

## Журнал

Встроенной области журнала нет ни в одном режиме: геометрия экрана не резервирует высоту под лог.
Runtime logging остаётся единственным хозяином application host и работает всегда, но показывается
только там, куда его направили:

- при `logging.viewer.enabled: false` — нигде на экране; bounded in-memory buffer сохраняется, а
  отдельные записи доступны в `/details` диагностического режима;
- при `logging.viewer.enabled: true` — в отдельном окне Windows Terminal, которое открывает само
  приложение. Оформление принадлежит Spectre.Console, а передача событий идёт по локальному
  одностороннему каналу только для текущего пользователя. Отдельная консоль не является вторым
  application host и не принимает команды управления состоянием.

Если отдельное окно недоступно, приложение сообщает об этом коротко и продолжает работу: журнал не
перенаправляется на экран TUI.

`AzurPilotLogViewerSession` сериализует открытие одного consumer-а. Пункт настроек «Открыть отдельную
лог-консоль снова» (`/viewer-reopen`) переиспользует живой канал либо создаёт новый после закрытия
viewer. Выключенный на старте viewer требует включения настройки и перезапуска. Закрытие host
дозаписывает bounded очередь, отменяет зависшие IPC операции и закрывает канал; viewer выходит по EOF.
Consumer не запускает новый application host.

Обычный вывод viewer компактен: время, уровень, категория и сообщение. Correlation и structured
properties остаются в событиях и доступны в диагностических `/details`; внутренний аргумент
`--log-viewer-details` включает их вывод отдельным consumer-ом. ANSI/markup экранируются,
известные поля секретов маскируются, размер события ограничен. `NO_COLOR` сохраняет своё стандартное
значение; цветовая приёмка требует терминала с поддержкой цвета.

Прежние `/environment-prepare` и `/mumu-stop` сохранены как технические aliases только в
`manual`/`diagnostic`, включая запрет прямого ввода в `normal`.

## История, ввод и resize

Экран состоит из строки состояния (target и режим), строки операции, закреплённого заголовка
истории, самой истории, отдельной области ввода и footer. Заголовок истории не участвует в
прокрутке и остаётся видимым при длинной ленте.

Composer визуально выделен: отдельный prompt, линия-разделитель и смена акцента при фокусе. Composer
принимает русский текст; стрелки вверх/вниз вне палитры перемещают историю команд с сохранением
черновика. `PgUp`/`PgDn` прокручивают историю, `Ctrl+End` возвращает к последним сообщениям; колесо
мыши над историей меняет только её прокрутку.

Цвет несёт семантику: нейтральный основной текст, приглушённое второстепенное, зелёный успех,
жёлтый внимание, красный отказ, акцент для выбранного пункта и активного ввода. Фон везде
наследуется от терминала, сплошных подложек и ярко окрашенных абзацев нет.

Сессия поддерживает изменение размеров окна. При размере меньше 60×18 отображается подсказка
увеличить терминал. Footer сокращает список клавиш на узких окнах, сохраняя подсказки `F4`, `Ctrl+C`
и `F2` при минимальном поддерживаемом размере. При выходе, Ctrl+C, отмене и исключении Terminal.Gui
освобождает терминал через dispose application lifecycle.

Все UI-вызовы и обновления views выполняются через один event loop. Операции запускаются асинхронно;
UI показывает текущий этап операции, а не выдуманный процент. История и log buffer ограничены по
размеру.

## Проверка

Headless checks покрывают operator use cases, каталог действий и правило доступа режимов, переходы UI
state, отмену и запрет повторной mutation. Терминальные ввод, resize и восстановление экрана
проверяются через настоящую Windows terminal boundary; захват через ConPTY/xterm.js подтверждает
поведение этой цепочки, но не заменяет проверку физического Windows Terminal. Live acceptance самого
приложения и exact MuMu описана в
[operator-tui-acceptance.md](../testing/operator-tui-acceptance.md); screenshot capability и native
frame ownership — в [screenshot-diagnostics.md](screenshot-diagnostics.md) и
[native-frame-ownership.md](native-frame-ownership.md).
