# Операторский TUI

Операторский TUI — одна из пользовательских поверхностей AzurPilot. В будущем он может работать рядом с
WebUI; Agent CLI остаётся отдельным машинным интерфейсом. В TUI доступны только уже реализованные
backend capabilities — пустых разделов для будущих игровых задач, настроек и расписаний нет.

## Границы

`AzurPilot.App` содержит composition root, application-level operator use cases и Terminal.Gui UI.
`OperatorUi` отвечает за renderer, клавиатурную навигацию и ограниченное состояние представления.
`OperatorServices` связывает выбранную пользователем capability с уже существующими сервисами MuMu,
Android, Azur Lane и screenshot diagnostics. UI не формирует команды ADB, не выбирает endpoint и не
дублирует lifecycle postconditions.

Интерактивный запуск использует тот же application host и один DI container, что и одноразовая
диагностика. Startup snapshot показывается в первой сессии без второго сбора диагностики; host
остаётся запущен до выхода из TUI. При неготовой или отсутствующей MuMu оболочка остаётся доступна и
показывает неизвестное/недоступное состояние. При недоступной native boundary startup failure также
виден в UI, а недоступные действия возвращают реальные отказы.

Если stdin или stdout перенаправлены, Terminal.Gui не запускается: приложение выполняет прежний
одноразовый диагностический путь. Человекочитаемый итог остаётся в stdout, structured JSON logs — в
stderr. Успешная строка итога сообщает о запуске application host и начальной диагностике, но прямо
указывает, что это не доказывает готовность MuMu, Android или Azur Lane. В интерактивном режиме тот же
logging stack пишет в bounded in-memory provider, который UI показывает в отдельной панели;
background-код никогда не пишет на активный экран напрямую.

## Выбор и действия

`/` или `F2` открывает палитру. Стрелки выбирают действие, `Tab` дополняет имя, `Enter` выполняет его,
`Esc` закрывает палитру. `/help` перечисляет доступные действия, а `/instances` обновляет фактический
MuMu inventory. По умолчанию instance не выбран: оператор выбирает точный `MuMuInstanceId` из списка.
Отображаемое имя служит подсказкой и не заменяет identity.

`/diagnostics` повторно собирает существующий диагностический snapshot. `/android` и `/game` наблюдают
состояние только для выбранного instance. Наблюдение не подготавливает transport и не запускает
эмулятор или игру. `Unknown` и недоказанные факты отображаются как неизвестные, а не как подтверждённое
отсутствие или готовность.

`/environment-prepare` — отдельное подтверждаемое действие для выбранного точного target. Оно запускает
MuMu только если наблюдение доказало состояние `Stopped`, пропускает lifecycle при `Running`, затем
разрешает endpoint того же target и подготавливает Android до transport/shell/boot readiness. Оно не
запускает Azur Lane. Недоказанное состояние или ошибка preflight прекращают выполнение до следующего
этапа; после уже выполненного старта MuMu может остаться запущенным при отказе или отмене. Повтори
наблюдение, прежде чем делать вывод о состоянии.

MuMu start/stop/restart, Android transport preparation и Azur Lane start/stop/restart требуют отдельного
подтверждения. По умолчанию подтверждение отменено; для согласия оператор должен явно выбрать его.
Выполнение проходит через существующие orchestration services, mutation gates и проверку результата.
Двойной ввод не запускает вторую операцию, пока занята текущая.

`/screenshot` выполняет один production capture для выбранной пары instance/endpoint, затем вызывает
production scanner для `FullFrame` и `Center`. UI показывает размеры, pixel bounds и полученные
агрегаты RGB. Эти статистики не определяют, какой экран игры отображён. Native frame освобождается
после сканирования и не сохраняется в истории.

Отмена прекращает текущую операцию по её cancellation contract. Она не откатывает уже выполненную
mutation и не останавливает MuMu/игру автоматически. Если результат неизвестен, сначала повторно
наблюдай состояние. `/exit` завершает сессию после отмены и завершения активной операции.

## История, ввод и resize

Операторские результаты и runtime logs разделены. PgUp/PgDn прокручивают историю независимо от
composer, `Ctrl+End` перемещает к последнему сообщению. F3 показывает или скрывает отдельную
полноширинную нижнюю панель журнала; `Alt+PgUp`/`Alt+PgDn` и `Alt+End` прокручивают её. Колесо мыши
над историей или журналом меняет только прокрутку соответствующей панели. `Ctrl+End` и `Alt+End`
возвращают соответствующую панель к новым сообщениям. Composer закреплён у нижней границы и принимает
русский текст; стрелки вверх/вниз вне палитры перемещают историю команд с сохранением draft.

Сессия поддерживает изменение размеров окна. При размере меньше 60×18 отображается подсказка увеличить
терминал. Footer сокращает список клавиш на узких окнах, сохраняя подсказки `F4`, `Ctrl+C` и `F2` при
минимальном поддерживаемом размере. При выходе, Ctrl+C, отмене и исключении Terminal.Gui освобождает
терминал через dispose application lifecycle.

Все UI-вызовы и обновления views выполняются через один event loop. Операции запускаются асинхронно;
UI показывает elapsed time, а не выдуманный процент. История и log buffer ограничены по размеру.

## Проверка

Headless checks покрывают operator use cases, переходы UI state, отмену и запрет повторной mutation.
Терминальные ввод, resize и восстановление экрана проверяются через настоящую Windows terminal
boundary; захват через ConPTY/xterm.js подтверждает поведение этой цепочки, но не заменяет проверку
физического Windows Terminal. Live acceptance самого приложения и exact MuMu описана в
[operator-tui-acceptance.md](../testing/operator-tui-acceptance.md); screenshot capability и native frame
ownership — в [screenshot-diagnostics.md](screenshot-diagnostics.md) и
[native-frame-ownership.md](native-frame-ownership.md).

### Follow-up: настраиваемый запуск игры

Полная команда, которая по настройке оператора автоматически запускает игру после подготовки Android,
пока не определена: текущая строгая схема не содержит `game.*`, а identity игры остаётся фиксированной.
Конкретный follow-up должен расширить этот же JSON-контракт до schema v3 со строгой секцией `game` и
обязательным boolean `launchAfterPreparation`. Legacy v1/v2 принимаются как прежде и нормализуются в
памяти к effective v3 с `false`; файл не записывается и автоматически не переписывается. Значение v3
проходит строгую проверку, второй YAML/JSON источник истины не появляется. Проверки подтверждают
нормализацию v1/v2, оба явных значения v3, default `false`, отказ для неверного типа и неизвестных
свойств.

Одна production orchestration должна для того же точного target последовательно доказать MuMu, Android
transport и boot readiness, затем наблюдать game state и запускать игру только при `true` и доказанном
состоянии `Stopped`. Если target уже `Running`, повторный запуск пропускается; `Unknown` завершает
сценарий отказом. Подтверждение перечисляет только действия, включённые настройкой и текущими фактами;
ошибка или отмена сообщает последний завершённый этап и возможное оставшееся состояние без
автоматического rollback. Тесты покрывают exact target, MuMu/Android/game `Running`/`Stopped`/`Unknown`,
уже запущенную игру, отказ и отмену после каждого этапа и postconditions. Orchestration владеет
порядком существующих lifecycle/readiness services, UI — только explicit confirmation и представлением
результата. Так сохраняются строгий конфиг-контракт, target identity и idempotence без дублирования
lifecycle в UI. До этого отдельного изменения `/environment-prepare` заканчивается Android readiness
и никогда не запускает Azur Lane.
