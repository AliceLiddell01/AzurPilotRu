# Проверка игровых операций

Контракты реализации и ограничения описаны в [архитектуре](../architecture/game-ui.md).
Общие команды сборки и native workflow принадлежат [getting-started](../getting-started.md).

## Постоянные проверки

`StableMainIgnoresChangingBackgroundAndRejectsOverlays` проверяет через native matcher три разных
синтетических фона при неизменных UI-кнопках и отказ Ready при известном/неизвестном содержимом
модального окна либо открытой левой панели на 720p–4K. Это не реальные фазы анимации: сохранённые
или новые реальные кадры проверяются отдельно во временном каталоге. Unknown-content fixture
содержит общий крест оформления окна, но не Update/Confirm. Guard не имеет области tap.
`OverlayGuardUncertaintyNeverProvesReadyOrTaps` проверяет пропущенный/неоднозначный/технический guard,
а `DialogAppearingAfterClassificationBlocksFreshActionWithoutTap` — окно на новом кадре перед вводом.

`uv run tests/tools/test_prepare_game_assets.py` проверяет генератор ассетов на искусственных
исходниках: отсутствие, повреждение, неверные формат/SHA256/размеры, непригодные рецепты,
отказы подготовки, резервного копирования и публикации, восстановление старых файлов и удаление
новых. Отдельно проверяются сохранение резервных копий при отказе восстановления, согласованность
контрольных сумм/размеров и байтовая повторяемость успешного запуска. Проверка входит в CI и не
требует пользовательских оригиналов; она не доказывает воспроизведение production-ассетов без
исходников, указанных в сведениях об их происхождении.

`GameGeometryTests` проверяет округление, весь кадр, точки на краях и отказ неподдерживаемых
ориентаций/размеров. `GameUiRecognizerTests` использует неперсональные UI-crops на искусственном фоне
для каждого поддерживаемого контрольного разрешения. Эти образцы доказывают преобразование координат, масштабирование и ROI,
но не доказывают нативную раскладку UI другого разрешения.
Отдельные crops реальных заголовков Depot/Technology не должны распознаваться как Dock.
Образцы режима выбора имеют совпадающий заголовок Dock и отдельный запрещающий Confirm; тесты Core
проверяют запрет ввода и отказ подтверждения результата при таком сочетании.

`GameUiActionRunnerTests` проверяет одно нажатие, новый кадр результата, устаревший кадр/неверное устройство, отсутствие и
неоднозначность исходного признака, небезопасные границы, отказ преобразования координат/ADB/захвата,
повторный ввод, изменение размера и отмену.
`GameInputViewportTests` проверяет rotation, физические/логические границы кадра, app bounds, display,
перекрытое окно, усечение и неизвестный формат. `GameUiAgentTests` использует рабочие механизмы захвата,
сопоставления, адаптер ввода и общую аренду через машинный envelope.

Native CTest `native_game_match` проверяет C ABI на сдвинутых контролируемых изображениях разных
размеров, конкурирующих кандидатах, низкой текстуре и ошибках ROI/бюджета. Проверка владения считает живые
кадры/RGB-байты при повторных поисках на 4K. Негативная managed проба отвергает DLL текущего ABI без
обязательного экспорта сопоставления до создания кадра.

`GameUiReadinessTests` проверяет независимость и устойчивость Ready, replay/stale/target/viewport/native
отказы, неизвестные guards, перекрытие при видимых main-кнопках, bounded пассивную загрузку,
единственный tap и отмену с сохранением эффекта. `GameUiReadinessAgentTests` проверяет существующий
lifecycle из Stopped, идемпотентность, общую lease, исчезновение exact target и смену endpoint.
`states.json` задаёт неперсональные синтетические композиции UI-crops; это не полные реальные экраны.
Синтетические login/server/download/update/main-overlay fixtures отличаются от живой приёмки.
Все source-примеры текущих новых crops — настоящие 4K-оригиналы; их rescale не доказывает нативный UI
на другом разрешении. Сборка и тесты не читают `assets_raw`.

Для live UI Ready отдельно нужны cold start, повторный ensure без lifecycle mutation/tap, возврат
из Dock, доступные login/download состояния и независимый итоговый capture/foreground.
Следуйте [live-testing skill](../../.agents/skills/azurpilot-live-testing/SKILL.md): read-only preflight
и отдельное актуальное подтверждение exact identity/границ mutation обязательны. Не провоцируйте logout,
обновление или награды для покрытия теста. Невстретившиеся live-состояния отмечаются `NOT_TESTED`.

## Реальные исходники и временные материалы

Полные снимки экрана и каталоги пользователя для тестов не требуются у другого разработчика.
Локальный `assets_raw/` в корне репозитория игнорируется Git целиком. Это необязательный архив
оригиналов для проверки UI, без зависимости сборки, тестов или runtime. Исходники сохраняются
неизменными; временные производные и метрики размещаются вне архива и отслеживаемых файлов.
В репозитории находятся только отобранные crops и обезличенные fixtures. Для локальной проверки
реальных изображений используй нативную границу и рабочий механизм распознавания, сохраняя в системном temp
только SHA256, размеры, статусы и ограниченные метрики. Разовые скрипты, исходные снимки,
обзорные листы и отчёты приёмки также остаются в temp, без импорта внешнего каталога в Git.

Отдельно отмечай: искусственные образцы; уменьшенные исходники; реальные кадры в исходном разрешении;
живой захват. Уменьшенный 4K-снимок не доказывает работу нативного 1080p UI. Ограниченные замеры
времени/памяти дополняют проверки владения, но не являются универсальным обещанием производительности.

## Безопасная живая проверка

Используй Agent CLI собранного проверяемого HEAD и сохраняй ограниченные JSON envelopes вне
отслеживаемых файлов. Выполняй следующую процедуру самостоятельно, без ручного ADB со стороны оператора:

1. Через `instances` и `resolve` подтверди exact identity запущенного MuMu; во всех дальнейших вызовах
   передавай её в `--target`. Endpoint разрешает продукт из текущего MuMu control surface.
2. Выполни read-only `android-observe`. При `Absent` выполни **один**
   `android-prepare --target <identity>`, который под общей арендой повторно разрешит target,
   подключит только исходный `Absent` и независимо докажет transport, shell и boot.
   Для исходного `Device` connect не выполняется. Если transport уже `Device`, но shell/boot ещё
   не готовы, та же явная команда допускает только существующее bounded ожидание.
3. При `Offline`, `Unknown`, неразрешённом endpoint или отказе подготовки остановись с конкретным
   failure/evidence. Не повторяй connect и не заменяй его `environment-prepare`: эта команда имеет
   более широкую capability и может запустить MuMu. Успешный stdout connect не является readiness.
4. После подготовки повтори `android-observe`: требуются `Device`, доступный shell и boot `1`.
   Затем выполни `game-observe`, `game-ui-observe` и `game-input-observe` read-only на том же target.
   Требуются доказанные foreground Global/EN, главный экран, допустимая геометрия и viewport.
   Неизвестный факт блокирует дальнейший шаг. Не перезапускай здоровую игру и не меняй разрешение.

Только после успешного preflight выполни **один** `game-dock-roundtrip` на уже открытом главном экране.
Команда заново подготавливает transport до первого кадра под той же арендой и на том же endpoint;
readiness не отменяет свежие проверки UI/viewport перед каждым нажатием. Она сохраняет сведения о происхождении четырёх кадров,
две точки, результаты сопоставления и отдельные результаты открытия/возврата. Успех требует обоих переходов.
При первом отказе сохрани ограниченный по объёму envelope и останови проверку. Отсутствие доказанного результата
не является доказанным отсутствием эффекта. Покупки, сбор наград, изменение кораблей/настроек и
прочие игровые действия этой проверкой не разрешаются.

В отчёте отделяй детерминированные регрессионные тесты от результатов живой проверки MuMu/ADB. Без подтверждённых
живых postconditions укажи `BLOCKED` с первым отказом либо `NOT_TESTED`, если сценарий не запускался.
Изменение transport (`androidPreparation`/`androidMutation`) не доказывает игровой переход:
для него нужны отдельные `open.changeProven` и `close.changeProven`.
