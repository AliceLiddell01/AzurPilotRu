# Приёмка операторского TUI

Headless tests проверяют production operator use cases, каталог действий, правило доступа режимов и
переходы ограниченного UI state. Они не подменяют фактическую терминальную границу. Перед выпуском TUI
отдельно проверяется на Windows x64 в Windows Terminal с PowerShell 7, а live capability — только на
явно выбранном или однозначно разрешённом MuMu instance. Захват в Windows ConPTY через xterm.js полезен
для проверки input, cell layout и resize, но не доказывает рисование или resize в физическом Windows
Terminal.

## Интерактивная терминальная сессия

Собери Release по каноническому workflow из [getting-started.md](../getting-started.md), затем запусти
`AzurPilot.App.exe` в открытой Windows Terminal сессии без перенаправления stdin/stdout. Проверь:

- открывается fullscreen TUI без рамки и без встроенной области журнала; `/` и `F2` показывают
  короткий первый уровень палитры, стрелки перемещают выбор, `Enter` открывает категорию или выполняет
  действие, `Esc` закрывает ровно один слой и возвращает на предыдущий уровень;
- в обычном режиме первый уровень содержит только пользовательские операции, а прямой ввод
  `/instances`, `/android-prepare`, `/screenshot` не исполняет внутреннюю операцию и объясняет, в каком
  режиме действие доступно и как туда перейти;
- `--mode manual` показывает категории `MuMu`, `Android`, `Игра`, `--mode diagnostic` дополнительно
  категорию `Диагностика`; переходы между категориями не плоские;
- неверный `--mode` завершает запуск отказом и не подставляет обычный режим молча;
- composer визуально выделен (prompt, линия-разделитель, акцент при фокусе); русские символы
  вводятся и вставляются; `Esc` после палитры не оставляет символ `/` и возвращает черновик;
- `/help` показывает только доступные в текущем режиме действия; startup status берётся из одного
  snapshot, и без явного выбора или однозначного разрешения target никакое MuMu/Android/game действие
  не запускается;
- `/environment-start` без выбранного instance сам разрешает точную identity по `mumu.instance` и
  предъявляет её в едином подтверждении; при нескольких экземплярах и `auto` оператор получает выбор
  точного ID, а старт остаётся запрещённым до однозначного выбора. Ручные `/instances` и `/select` для
  этого не требуются;
- `/environment-start` стартует MuMu только из доказанного `Stopped`, пропускает перезапуск при
  `Running`, использует endpoint того же target и проверяет Android transport/shell/boot readiness;
  игра не запускается. `Unknown` и ошибки preflight fail closed, а после уже выполненного старта MuMu
  может остаться запущенным при отказе или отмене;
- «Настройки» реально сохраняют точный ID и YAML; повторный запуск восстанавливает ID, режим и
  отдельный viewer. Legacy JSON мигрируется по явному сохранению, backup показывается в результате;
- `/game-start` из `Stopped` сам подготавливает окружение перед game lifecycle, с одним подтверждением;
- полный прямой ввод `/screenshot` или `/android` в соответствующем режиме выполняет команду,
  а не выбирает первую категорию; `normal` запрещает и прежние technical aliases;
- confirmation mutation по умолчанию выделяет «Отмена»: `Enter`, `Esc` или выбор отмены не запускают
  service; подтвердить можно только отдельным явным выбором;
- `PgUp`/`PgDn` прокручивают историю, `Ctrl+End` возвращает к последним сообщениям, колесо мыши над
  историей меняет только её прокрутку; заголовок истории остаётся видимым при длинной ленте;
- проверь footer и resize одной сессией 120×30 → 100×30 → 80×25 → 60×18 → 59×17 → 120×30: `F4`,
  `Ctrl+C` и `F2` остаются видимы на всех поддерживаемых размерах, ниже 60×18 отображается
  предупреждение, возврат восстанавливает выбранный target и компоновку;
- отмена долгой операции и выход восстанавливают экран, курсор и terminal input state.

Если stdin или stdout перенаправлены, приложение должно завершить одноразовую диагностику, а не ждать
клавиши, не писать terminal control sequences и не открывать отдельное окно журнала. Проверяй оба
потока раздельно. При успехе итог stdout должен говорить только о запуске host/начальной диагностике и
явно не подтверждать готовность MuMu, Android или Azur Lane; structured JSON не должен попадать в
stdout.

## Отдельная лог-консоль

При `logging.viewer.enabled: false` окно не открывается, в TUI нет ни панели журнала, ни
зарезервированной под неё высоты, а runtime logging продолжает работать.

При `logging.viewer.enabled: true` отдельно открывается окно Windows Terminal с живыми событиями
application host:

- уровни INFO/WARNING/ERROR различимы по семантике цвета, а не только по тексту;
- ключевые значения подсвечены, длинные абзацы не окрашены целиком;
- вывод основного TUI не пересекается с выводом отдельного окна;
- управляющие последовательности из текста записи не исполняются терминалом отдельного окна;
- завершение приложения не оставляет осиротевших процессов, а обрыв канала не ломает основной TUI;
- повторное открытие через настройки не дублирует живое окно и восстанавливает consumer после закрытия;
- компактный вывод не дублирует correlation/properties; внутренний `--log-viewer-details` открывает
  подробный формат. При проверке цвета учти стандартную переменную `NO_COLOR` у тестового процесса;
- при недоступном `wt.exe` приложение сообщает об отказе коротко, продолжает работу и не перенаправляет
  журнал на экран TUI.

## Live MuMu и screenshot

Перед live шагами запиши bounded preflight состояния среды. Выполняй действия из самого
`AzurPilot.App.exe`, не из acceptance executable и не из отдельной ADB-команды:

1. Убедись, что `mumu.instance` задаёт однозначный target (явный `mumu:<index>` либо `auto` при ровно
   одном обнаруженном экземпляре). Не используй display name и не полагайся на «первый» экземпляр.
2. Выполни read-only `/status` и, в ручном или диагностическом режиме, `/android` и `/game`. Сохрани
   наблюдённые факты либо ограниченную причину, по которой состояние не удалось доказать. Эти команды
   не подключают ADB, не запускают MuMu и не меняют игру.
3. Различай пассивное наблюдение и подтверждённую подготовку:
   - Если проверяется только `/android` или `/game`, недоступность endpoint/readiness относится к этому
     read-only результату. Не запускай MuMu и не подключай ADB лишь для получения положительного ответа.
   - `/environment-start` — единое подтверждаемое действие. Оно повторно разрешает точную identity и
     наблюдает host-side состояние внутри production use case. При доказанном `Stopped` действие может
     запустить этот MuMu; при `Running` пропускает запуск. `Stopped` не является ошибкой предусловия.
     Read-only `android_endpoint_unavailable` до запуска не запрещает этот сценарий: endpoint и Android
     readiness разрешаются после host-side шага.
   - Если exact identity не разрешена, host-side состояние `Unknown` или discovery/наблюдение MuMu
     завершается реальным отказом, use case должен fail closed до последующих lifecycle/Android действий.
     Если отказ возникает уже после запуска MuMu на этапе endpoint/readiness, зафиксируй его фактическую
     stage и failure code; не представляй его как отказ предусловия до запуска. Частичное изменение
     состояния сохраняется без compensating stop.
4. После подготовки независимо повтори наблюдение состояния. Успех запуска приложения или MuMu сам по
   себе не доказывает готовность Android: positive readiness требует exact endpoint, transport `Device`,
   доступный shell и `boot_completed=1`.
5. Выполни production `/screenshot` только после доказанной текущей Android readiness. Убедись, что один
   capture породил `FullFrame` и `Center` scan с фактическим размером, bounds и aggregate RGB statistics;
   не трактуй цветовую статистику как распознавание экрана. Не запускай Azur Lane только ради захвата.

Если exact instance отсутствует или identity/host-side состояние не доказаны, сохраняй конкретную причину
и не продолжай mutation через другой target или fallback. Если Android endpoint/readiness отсутствовали
до подтверждённого `/environment-start`, это само по себе не является `BLOCKED` для подготовки.
Выполняй её только через production orchestration, с отдельным явным подтверждением и точным target.
После теста восстанови исходное известное host-side состояние через production lifecycle-команду и
независимо подтверди postcondition наблюдением.

Проверь также `/environment-stop`: он должен остановить именно разрешённый target, показать
объяснённое подтверждение и подтвердить результат фактическим postflight. Игра этим действием не
затрагивается.

Если понадобится автоматически запускать Azur Lane после подготовки, это отдельная capability, которой
в текущей схеме конфигурации нет: `game.*` не заводится заранее, а identity игры остаётся фиксированной.
Текущая приёмка `/environment-start` заканчивается доказанной Android readiness и не запускает игру.

Evidence отчёт ограничивается build identity, выбранным точным target, подтверждёнными фактами до/после,
кодами отказа и итогом ROI scan. Не сохраняй screenshot bytes, полный вывод внешних команд, полный список
процессов или machine-specific секреты. Acceptance executable остаётся полезным для собственных
контрактов, но его результат не доказывает работоспособность TUI.
